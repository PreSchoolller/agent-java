# 应用抽象层设计

> 状态：设计阶段，未实现。接口未冻结。

---

## 一、实现分工

**本文件描述的这一层，代码只由项目作者本人实现。**

- 任何 AI 助手 / agent 不得代为编写这一层的代码，也不得修改相关的 `app/`、`spi/` 源码。
- 助手可以做的事，边界仅此：评审接口设计、指出矛盾、解释概念、补充文档。
- 这一层决定 `backend` / `frontend` 的最终边界，属于后端核心工作。代工产出的接口只是"看起来对"，错误要到第二个前端出现时才暴露。
- 如果某个助手在本文件追加"已实现"字样或提交了这部分代码，视为越界，应回滚。

---

## 二、目标

在 `frontend` 与 `backend` 之间放一层应用抽象，使得：

1. **前端可替换**：Swing、TUI、JS 只是同一份状态的三个渲染器，换前端不重写状态逻辑。
2. **前端零持久化**：前端只持内存态，不碰磁盘、不读配置、不管恢复；持久状态由核心持有并投影出来。
3. **可无头运行**：不启动任何 UI，仅通过接口驱动完整对话（提交、流式、取消、审批）。

## 三、非目标

- 不改 `backend` 的领域语义（agent loop、provider、tool 的执行方式不动）。
- 不与 `spi` 的插件能力面（`PluginPersistentHelper` / `PluginShutDownJobHelper` / `ToolHelper` / `AgentJavaSessions`）合并，见第十节。
- 不要求一次设计到位，首个可运行版本只覆盖单会话一轮对话。

## 四、前置约束

以下两项不属于本层，但不解决则本层无法成立。

### 4.1 消息需要稳定标识

当前 `Message` 是 8 字段 record，**没有 id**；更新靠传对象引用：

```java
public record Message(String role, String text, long time, String toolName,
                      String toolArgs, String toolStatus, String callId, String thinking)

public Message updateMessageText(String id, Message target, String text)
public Message updateMessageContent(String id, Message target, String text, String thinking)
public Message completeToolCall(String id, Message target, String result, ...)
```

事件流必须能寻址"哪一条消息变了"。对象引用跨不了进程，也跨不了语言；后台任务回填与前台流式并发更新同一条消息时，引用语义更脆弱。前端要做按键增量更新（React 的 key、TUI 的行缓存），也需要一眼能认的稳定 key。

改造点：

- `ConversationStore` 中 6 个按引用更新的方法改为按 `messageId`
- `Main` 及各消费方调用点
- 落盘格式：`Message` 现按 role 字符串序列化，加 id 需处理旧文件兼容（读时补 id 或一次性迁移）

这是整层成本最高的前置改造，工作量大于接口定义本身。

### 4.2 读取必须保证全量

`Conversation` 有 `loaded` / `loader` 懒加载：从索引装载的会话 `messages` 为空，需触发 loader 才补齐。

对外契约必须改为：**读一个会话，返回的一定是全量消息**，内部负责触发加载。否则前端会拿到空列表并误判会话为空。

## 五、四种流量

| 方向 | 流量 | 内容 |
|---|---|---|
| 前端 → 核心 | 意图 | 提交、取消、切换会话、改配置 |
| 核心 → 前端 | 状态增量 | 带 `seq` 的事件流 |
| 核心 → 前端 | 宿主请求 | 需要前端应答才能继续（审批、补充输入） |
| 前端 → 核心 | 应答 | 按 `requestId` 配对 |

前两种是常规单向数据流。后两种是**反向交互**，无法并入事件流：它不是通知，是等待应答的请求。三种前端的弹窗形态完全不同（Swing 模态框、TUI 确认行、JS 卡片），若抽象层把它做成回调 `Supplier<Boolean>`，三边都要各自实现弹窗生命周期。

## 六、投影类型

纯数据，无持久化、无 UI 类型。前端的全部渲染输入来自这里。

```java
record Snapshot(long seq, List<SessionSummary> sessions, String activeSessionId) {}

record SessionSummary(String id, String title, boolean pinned, String workspace,
                      SessionStatus status, long updatedAt) {}

record SessionView(String id, String title, String workspace, SessionStatus status,
                   String modelName, String modelProfile, String reasoningEffort,
                   String agentMode, UsageView usage, List<MessageView> messages) {}

record MessageView(String messageId, String clientMsgId, Role role, String text,
                   String thinking, long time, MessageState state, ToolView tool) {}

record ToolView(String name, String argsSummary, String statusDetail, String callId) {}

record UsageView(long inputTokens, long outputTokens, double elapsedSeconds) {}

enum SessionStatus { IDLE, RUNNING }

enum MessageState { PENDING, CONFIRMED, REJECTED, CANCELLED, FAILED, SUPERSEDED }
```

`MessageView` 的两个 id 是乐观更新的全部成本：`messageId` 由核心给，`clientMsgId` 由前端给。

## 七、接口

### 7.1 最小面

只求无头跑通一轮对话：建会话、发一句、看到流式、能取消、能答审批。

```java
interface AppView {
    Snapshot snapshot();
    SessionView session(String sessionId);
}

interface AppCommands {
    String createSession(String workspace);
    void selectSession(String sessionId);
    void submit(String sessionId, String clientMsgId, String text);
    void cancel(String sessionId);
}

interface AppEvents {
    AutoCloseable subscribe(long sinceSeq, EventListener listener);
}

interface HostRequests {
    List<Request> pending();
    void answer(String requestId, Answer answer);
}
```

`rename` / `pin` / `delete` / `fork` / `regenerate` / 各类 `setXxx` 不影响"能否跑通"，不进最小面。

### 7.2 查询

```java
interface AppView {
    Snapshot snapshot();
    SessionView session(String sessionId);
    List<SessionSummary> sessionsSince(long seq);
}
```

`Snapshot` 与 `Seq` 必须原子返回，理由见 8.1。

### 7.3 命令

```java
interface AppCommands {
    // 会话
    String createSession(String workspace);
    String ensureSession(String sessionId, String workspace);
    void selectSession(String sessionId);
    void renameSession(String sessionId, String title);
    void pinSession(String sessionId, boolean pinned);
    void deleteSession(String sessionId);
    String forkSession(String sessionId, String fromMessageId);

    // 对话，全部异步、立即返回
    void submit(String sessionId, String clientMsgId, String text);
    void regenerate(String sessionId, String fromMessageId);
    void cancel(String sessionId);

    // 会话级配置
    void setWorkspace(String sessionId, String workspace);
    void setModel(String sessionId, String profileName, String modelName);
    void setReasoningEffort(String sessionId, String effort);
    void setAgentMode(String sessionId, String mode);
}
```

`ensureSession` 面向"外部已持有会话 id"的场景，语义为幂等 upsert：已存在则复用且不改 workspace，仅新建时生效。

### 7.4 事件

```java
sealed interface StateEvent { long seq(); String sessionId(); }

record SessionCreated(SessionSummary s, long seq)              implements StateEvent {}
record SessionRemoved(String sessionId, long seq)              implements StateEvent {}
record SessionRenamed(String sessionId, String title, long seq) implements StateEvent {}
record SessionPinned(String sessionId, boolean pinned, long seq) implements StateEvent {}
record ActiveSessionChanged(String sessionId, long seq)        implements StateEvent {}

record MessageAppended(String sessionId, MessageView m, long seq) {}
record MessageDelta(String sessionId, String messageId,
                    String textDelta, String thinkingDelta, long seq) {}
record MessageCompleted(String sessionId, String messageId, long seq) {}
record ToolStatusChanged(String sessionId, String messageId,
                         String status, String result, long seq) {}

record UserMessageConfirmed(String sessionId, String clientMsgId,
                            String messageId, long seq) {}
record UserMessageRejected(String sessionId, String clientMsgId,
                           String reason, long seq) {}

record RoundStarted(String sessionId, long seq)                implements StateEvent {}
record RoundFinished(String sessionId, UsageView usage, long seq) {}
record RoundFailed(String sessionId, String reason, long seq) {}
record RoundCancelled(String sessionId, long seq)              implements StateEvent {}

record ConfigChanged(String key, String sessionId, long seq) {}
```

`MessageDelta` 需由核心按帧合并后推送。逐 token 直推会压垮终端刷新，也会把 HTTP 打成大量小包。

### 7.5 审批

```java
interface HostRequests {
    sealed interface Answer {}
    record Approve()             implements Answer {}
    record Reject(String reason) implements Answer {}
    record Text(String value)    implements Answer {}

    record Request(String requestId, String sessionId, Kind kind,
                   String payload, long deadlineEpochMs) {}
    enum Kind { TOOL_APPROVAL, USER_INPUT, CONFIRM }

    List<Request> pending();
    void answer(String requestId, Answer answer);
    void cancel(String requestId);
}
```

三种应答形态分开，避免出现"传一半参数是废值"的万能签名。`pending()` 供前端重启后补拿未答请求——否则正在等审批的会话会静默挂死。

### 7.6 配置

```java
interface RuntimeConfig {
    List<ProfileView> profiles();
    String activeProfile();
    void setActiveProfile(String name);
    List<String> enabledTools();
    void setEnabledTools(List<String> names);
    String defaultWorkspace();
    void setDefaultWorkspace(String path);
    List<McpServerView> mcpServers();
    String toolProperty(String toolId, String key);
    void setToolProperty(String toolId, String key, String value);
}
```

`AppSettings` 的字段分三类，不能整包搬：

| 类别 | 字段 | 归属 |
|---|---|---|
| 纯 UI 偏好 | `uiTheme`、`contentFontSize`、`window*`、`settingsDialog*`、`sidebarDivider`、`minimizeToTray`、`approvalSound/SystemNotify/BringToFront` | 各前端自己存（properties / localStorage / rc 文件） |
| 运行时配置 | `profiles`、`enabledTools`、`activeProviderNames`、`activeContextHandler`、`mcpServers`、`toolProperties`、`defaultWorkspace` | 核心，换前端必须跟着走 |
| 基础设施 | `logConsole*`、`logFile*` | 启动参数，不进本层 |

"前端零持久化"最难的一步在这里：把 UI 偏好从配置里摘出去，而不是搬文件。

### 7.7 装配

```java
interface AgentApp extends AppView, AppCommands, AppEvents, HostRequests, RuntimeConfig {}
```

拆 facet 而不合成肥接口：JS 侧的 HTTP 映射可分端点，TUI 只取子集，测试替身不必实现无关方法。

## 八、契约中必须明确的细节

这十条决定三种前端能否写出同一套逻辑。每条都标了不照做的后果。

### 8.1 快照与 seq 的原子性

`Snapshot` 携带 `seq`，订阅从该 seq 起消费。**取快照与打 seq 必须在同一临界区内完成。**

若拆成"先 `sessions()` 拿全量，再 `subscribe(sinceSeq)`"，两步之间的事件会永久丢失：拿到旧列表、错过中间变更、新 seq 已越过那段区间。

替代方案是"先订阅再取快照"（用快照覆盖本地并丢弃快照前事件），对核心压力更小，但前端要去重。采用前者，实现时不要图省事拆开。

### 8.2 消息文本的归属

`submit` 后前端本地先插一条 `PENDING` 空消息，核心也会 append 一条。**这条 `MessageAppended` 里的 `text` 是空还是全文，必须写进契约。**

规则：

- `Role.USER`：append 时带全文，无 delta。用户消息内容不会变。
- `Role.AI`：append 时 `text` 为空，内容只从 `MessageDelta` 累积。

不统一则前端会重复计入正文，或者渲染一条永远空着的消息。

### 8.3 乐观更新的配对与孤儿

前端生成 `clientMsgId` 渲染 PENDING，核心回 `UserMessageConfirmed(clientMsgId, messageId)` 配对转正，或 `UserMessageRejected` 标记失败。

**孤儿问题**：前端崩溃后，核心那边那条 PENDING 永远等不到配对（`clientMsgId` 随进程消失）。

处理规则（择一，实现前定）：

- 核心不持久化 PENDING，收到 `Confirmed` 才落盘 —— 语义最干净（没确认即未发生），要求 append 的落盘时机与确认对齐
- 先落盘，启动时扫描清理为 `REJECTED`
- 前端把 PENDING 视作请求级事务，超时自动回滚

### 8.4 消息状态的取值边界

`MessageState` 需要覆盖：被取消那一轮里的半截消息、流式中途失败的消息、被重跑作废的旧消息。六态（`PENDING` / `CONFIRMED` / `REJECTED` / `CANCELLED` / `FAILED` / `SUPERSEDED`）是下限，语义需逐条写清，否则前端只能把它们都当灰色处理。

### 8.5 取消语义

`cancel` 幂等：对已结束的会话调用不应报错，也不应产生第二条 `RoundCancelled`。

取消后已产生的半截内容保留还是删除，与上下文是否包含它绑定，见第九节决策 4。

### 8.6 为什么没有 editMessage

"改一条历史消息"在 agent 上下文里等于"截断到该点并重跑"，与 `regenerate` 是同一动作。拆成两个方法，前端要么只用其中一个（另一个是死方法），要么两个都调（重跑两次）。因此只保留 `regenerate(sessionId, fromMessageId)`。

### 8.7 审批的超时

`ToolApprovalGate` 的契约是「实现可以阻塞等待用户点击」，`boolean allow(...)` 无超时，在工具执行线程上同步阻塞。

无头模式下没有前端应答，**这一轮会永久挂死**。因此 `Request` 必须带 `deadlineEpochMs`，并定义超时后的默认动作；或提供"无前端时自动放行/自动拒绝"的策略开关。此项不能留空，见决策 5。

### 8.8 工具参数的表达

现有 `appendToolCall(id, toolName, argsSummary, callId)` 传的是摘要。摘要用于展示，原文用于脚本前端读取完整参数，一个字段装不下。`ToolView.argsSummary` 只承担展示用途；需要原文时另行设计字段，见决策 7。

### 8.9 配置变更事件

`RuntimeConfig` 的 setter 必须产生 `ConfigChanged`。否则多前端同开时（Swing 与 JS 并存），一侧改了模型，另一侧永远不知道。

### 8.10 未读状态的归属

多会话列表需要显示"哪个会话有动静"。两个前端同开同一会话时，"已读"是全局还是本地，是产品决策：

- 全局：A 读过后 B 不再显示红点，多设备体验差
- 本地：核心不持有该概念，不进 `SessionSummary`

**先定归属，再决定是否进投影类型**，否则会渗进去后难以移除。

## 九、待定决策

实现前需逐条拍板，不预设答案。

| # | 问题 | 选项 | 影响 |
|---|---|---|---|
| 1 | seq 粒度 | 全局单调 / 每会话 seq + 列表版本号 | 锁竞争、带宽、前端合并复杂度 |
| 2 | 未读归属 | 核心状态 / 前端本地 | 是否进 `SessionSummary`、多设备一致性 |
| 3 | Delta 合并粒度 | 逐 token / 按帧（约 50ms） / 按内容块 | 终端刷新压力、HTTP 包数、首字延迟 |
| 4 | 取消后内容保留 | 保留半截并标记 / 整条删除 | 上下文是否含半截内容、能否重试 |
| 5 | 无前端时审批策略 | 自动拒绝 / 自动放行 / 挂起等超时 | 无头模式能否跑完一轮 |
| 6 | 单会话并挂多个审批 | 队列串行 / 并行 | 前端 UI 复杂度、工具并发度 |
| 7 | 工具参数 | 只给摘要 / 摘要 + 原文 | 脚本前端能否读取完整参数 |
| 8 | PENDING 落盘时机 | 确认才落盘 / 先落盘后清理 | 孤儿消息语义、崩溃恢复 |
| 9 | 附件与图片 | 若暂不支持则明确声明 | 将来加入会改 `submit` 签名与 `MessageView` |
| 10 | 配置拆分顺序 | 先摘 UI 偏好 / 先搬运行时配置 | 迁移风险与可回滚性 |

全局 seq 并非显然更优：它要求所有会话写入串行打号，后台会话与前台并发时存在锁竞争，单会话订阅还要跳过大量无关事件。每会话 seq 加独立列表版本号可避开这两点，代价是前端要合并两个序。

## 十、边界

### 10.1 与插件能力面的区别

| | 插件能力面（`spi`） | 应用抽象层（本文件） |
|---|---|---|
| 调用方 | 同 JVM 内的插件 | 任意前端（进程内 / 跨进程 / 跨语言） |
| 解决的问题 | 插件向宿主借能力（读配置、注册退出钩子、取工具列表、驱动会话） | 前端驱动整个应用（状态从哪来、意图往哪去） |
| 状态 | 无状态，纯转发 | 持有唯一状态树 |
| 形态 | 静态门面 + `install` 注入 | 实例 + 订阅 |

两者在"驱动会话"上有交集，但不合并。合并后插件能看到整套前端状态，前端能看到插件注册能力，两侧都被污染。

### 10.2 禁止出现的类型

方法签名中不允许出现 `Path`、`File`、`Properties`、`java.awt.*`、`javax.swing.*`、`SwingUtilities` 及任何 EDT 相关 API。出现任意一个，说明该处已退化为 Swing 适配器。

### 10.3 不负责持久化实现

本层只回答"状态从哪来"，不回答"存在哪个文件"。持久化是实现细节，藏在 `AppView` 背后。

## 十一、验证

### 11.1 假前端

不依赖真实实现即可判断投影是否够用：写一个 200 行内的 stdout 前端——订阅事件并打印 `MessageView` / delta / 工具状态变化，stdin 读一行生成 `clientMsgId` 后 `submit`，遇 `HostRequest` 在终端问 y/n 后 `answer`。能连续跑 3 轮对话、1 次取消、1 次审批即算够用。

写不出来，或需要偷看内部状态才能正确打印，说明状态投影缺东西。这比等第二个真前端写完再发现问题便宜两个数量级。

### 11.2 判据

- 方法名出现"下拉框 / 按钮 / 面板 / 对话框"：抽象到了控件层，退回去重抽
- 某方法只有一种前端会调：它不是本层的东西
- 遮住参数名只看类型仍能猜出用途：类型选对了；到处是 `String` 则没有
- 流式输出仅靠 apply 增量即可渲染正确：投影与事件完备

### 11.3 反例

出现任一条即说明设计走歪：

- 前端为显示正确需额外调用超过 2 个查询接口
- 需轮询才能知道一轮是否结束（应有 `RoundFinished`）
- 需在两个接口之间传内部对象引用
- 某前端需访问文件系统才能恢复会话列表

## 十二、落地顺序

1. 消息稳定 id（4.1）—— 没有这一步，其余全是空转
2. 快照原子性 + 单会话全量读取（4.2、8.1）
3. 最小面接口 + stdout 假前端
4. 补齐完整面，同时把 Swing 侧逐步改为消费投影
5. `RuntimeConfig` 三类拆分
6. JS / HTTP 适配器

第 1、2 步属于已有代码改造，不是新增抽象，且都不可回退——先做这两件。
