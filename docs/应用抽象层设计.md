## 一、边界

| 谁 | 负责 | 不负责 |
|---|---|---|
| 作者 | 实现 `AgentApp`（含 `AppView` / `AppCommands` / `AppEvents` / `HostRequests` / `RuntimeConfig`） | 前端 |
| 前端（`frontend` + `SwingApp`） | 建窗、订阅事件、把 UI 动作翻译成命令、渲染投影 | 不实现接口、不写会话仓库、不认识任何 core 实现类 |

`Main.main` 是唯一入口：

```java
SwingApp.start(null);   // 实现就绪后改成 SwingApp.start(new YourAgentApp(...));
```

传 `null` 时窗口照常打开，消息区显示"核心未就绪"，发送/重新生成/停止/新建都会提示并返回。
`Main` 除启动与两个插件静态桩（`apiEnsureSession` / `apiInject`，未就绪时抛异常）外没有别的内容。

## 二、前端怎么调接口

```
Window ──输入/重新生成/停止/侧栏操作──▶ SwingApp/Sidebar.Sessions ──命令──▶ AgentApp
   ▲                                                                        │
   └──────── SwingRenderer ◀── StateEvent ── subscribe ─────────────────────┘
```

### 命令映射

| UI 动作 | 调用 |
|---|---|
| 输入框回车 | `submit(sessionId, UUID, text)` |
| 重新生成 | `regenerate(sessionId, null)` |
| 停止 | `cancel(sessionId)` |
| 新建对话 | `createSession(workspace, activeId)` |
| 切换对话 | `session(id)` 拉投影后重建 |
| 重命名 / 置顶 / 删除 | `renameSession` / `pinSession` / `deleteSession` |
| 分叉 | `forkSession(sessionId, messageId)` |
| 模型 / 思考强度 / 权限模式 | `setModel` / `setReasoningEffort` / `setAgentMode` |
| 审批卡允许/拒绝 | `answer(requestId, Approve / Reject)` |

侧栏的数据源是 `Sidebar.Sessions`（`Window` 实现）：`sessions()` 实时取 `snapshot()`，
`messages(id)` 取 `session(id).messages` 供搜索与导出，写操作全部转成上面的命令。
消息区首次进入用 `SessionView.messages` 建卡，之后只吃事件。

### 事件消费

| 事件 | 前端行为 |
|---|---|
| `MessageAppended` | 按 `MessageView.role` 建卡：USER / ASSISTANT / TOOL_RESULT |
| `MessageDelta` | 找 `messageId` 对应的 AI 卡，追加正文/思考 |
| `MessageCompleted` | `finish()` 该卡 |
| `ToolStateChanged` | `RUNNING` → 标记执行中；其余终态 → `finish(resultText, success)` |
| `HostRequestOpened` | 按 `request.callId` 找工具卡，挂审批 future；用户点完 `answer` |
| `SessionCreated/Removed/Renamed/Pinned` | 刷新侧栏；当前会话被删时落到第一个 |
| `RoundStarted` | 生成态置 true |
| `RoundFinished` | 有 usage 就刷胶囊；`chainEnded=true` 才关生成态 |
| `RoundFailed` / `RoundCancelled` | 关生成态 + 提示 |
| `UserMessageRejected` | 提示"消息未发送：原因" |
| `Notice` | 画一张只读通知卡 |
| `GapDetected` | 提示事件缺口（尚未自动重拉） |

渲染器把所有窗口调用切到 EDT；句柄的注册、增量、收尾都排进同一队列，避免"先 remove 后 put"。

## 三、实现方要满足的语义

1. **seq 单调**，`subscribe(sinceSeq, listener)` 从 `sinceSeq` 之后开始投递；有缺口发 `GapDetected`。
2. **`MessageAppended` 是消息的唯一出生点**：之后所有 `MessageDelta` / `MessageCompleted` / `ToolStateChanged` 都用同一个 `messageId`，且必须先有 Appended。
3. **`MessageView.tool.callId` 与 `HostRequestOpened.request.callId` 必须一致**，前端靠它找卡片。
4. **AI 占位消息的 `text` 可以为空**，正文靠 `MessageDelta.textDelta` 推；思考走 `thinkingDelta`，不要拼进正文。
5. **`RoundFinished.chainEnded=false` 表示这条链还有续轮**，前端不关生成态；只有 `true` 才关。
6. **审批找不到卡片时前端会自动 `Reject("no card")`**，实现方不必等超时。
7. **`createSession(workspace, reuseIfEmptySessionId)` 的 `reuse` 是前端当前会话**：为空时改绑工作区并返回同一 id，`reused=true`。
8. 事件可以从任意线程发，前端负责切 EDT；但同一会话的事件必须按 seq 顺序到达。

## 四、已知缺口

**契约本身**

- `HostRequests.cancel(String requestId)` 与 `AppCommands.cancel(String sessionId)` 签名完全相同，`AgentApp` 上只剩一个 `cancel` 语义。前端目前只调 `answer`；要支持"撤回审批"，得先改名（如 `cancelRequest`）。
- 没有工具参数增量事件，工具卡只能显示 `MessageAppended` 时的 `argsSummary` 和终态结果。
- 没有"终止后台任务"的命令，工具卡不挂终止按钮（`BackGroundTaskControl` 未注册）。
- `Request.deadlineEpochMs` 只是字段，超时行为由实现方定义；`pending()` 的生命周期也要实现方自己收。

**前端**

- 设置面板仍直接读写 `AppSettings`（profile / MCP / 工具开关）：`RuntimeConfig` 只有只读投影与少量写方法，没有增删改命令。
- 模型下拉的选项目录仍读 `AppSettings`；选中值已经走 `SessionView` + `setModel`。
- `Notice` 画在消息流里，不是悬浮提示。
- `ConversationStore` 与 `frontend/store` 仍在仓库里，但生产路径已不引用（仅 GUI 测试用它造数据）。

## 五、验收

构建必须在 `app/` 下（根 `pom.xml` 不声明 modules，在根跑 `mvn` 是空操作）：

| 命令 | 期望 |
|---|---|
| `cd app && mvn -q -DskipTests compile` | 退出码 0 |
| `cd app && mvn -q test` | 95 个用例，3 个既有失败（`s09_toolCard` 工具卡折叠、`LazyLoadTest`、`PersistenceTest.t04`，在 `8d16d18` 上同样失败） |
| 启动 | 窗口打开，消息区显示"核心未就绪"；点发送会提示且不写库 |

实现 `AgentApp` 之后，最小闭环是：发一条消息 → 收到 `MessageAppended(USER)` → `RoundStarted` → `MessageAppended(ASSISTANT)` → 若干 `MessageDelta` → `MessageCompleted` → `RoundFinished(chainEnded=true)`。
