## 一、实现分工

**本文件描述的这一层，代码只由项目作者本人实现。**

- 任何 AI 助手 / agent 不得代为编写这一层的代码，也不得修改相关的 `app/`、`spi/` 源码。
- 助手可以做的事，边界仅此：评审接口设计、指出矛盾、解释概念、补充文档。
- 这一层决定 `backend` / `frontend` 的最终边界，属于后端核心工作。代工产出的接口只是"看起来对"，错误要到第二个前端出现时才暴露。
- 如果某个助手在本文件追加"已实现"字样或提交了这部分代码，视为越界，应回滚。

这条约束不能只活在本文件里——不打开 `docs/` 的 agent 看不到它。README 或仓库级 agent 指令里需要一份同样的声明，否则约束只对"恰好翻到这一页"的人生效。

## 二、目标

在 `frontend` 与 `backend` 之间放一层应用抽象，使得：

1. **前端可替换**：Swing、TUI、JS 只是同一份状态的三个渲染器，换前端不重写状态逻辑。
2. **前端零持久化**：前端只持内存态，不碰磁盘、不读配置、不管恢复；持久状态由核心持有并投影出来。
3. **可无头运行**：不启动任何 UI，仅通过接口驱动完整对话（提交、流式、取消、审批）。

## 三、非目标

- 不改 `backend` 的领域语义（agent loop、provider、tool 的执行方式不动）。
- 不与 `spi` 的插件能力面（`PluginPersistentHelper` / `PluginShutDownJobHelper` / `ToolHelper` / `AgentJavaSessions`）合并，见第十节。
- 不接管各前端的展示态（当前选中会话、滚动位置、输入框草稿），见 8.11。
- 不要求一次设计到位，首个可运行版本只覆盖单会话一轮对话。

## 四、前置约束

四项都不属于本层，但不解决则本层无法成立。它们都不产出本层对外的接口，却决定了最小面接口写完有没有地方跑。

落地顺序是 **4.2 → 4.3 → 4.1**：先做纯机械的搬家，再做语义变更（加 id），最后抽端口。4.4 不是改造，是投影实现的约束，不参与排序。

### 4.1 agent 链必须脱离 UI

`Main` 是纯静态类，`window` 是静态字段，`main()` 第一件事就是 `new Window("Agent")`，之后所有回调都挂在窗口上。`Main` 对 `Window` 的依赖是 17 个方法、26 处调用，方向分两种：

改造分两半：**出站抽端口，入站归组合根**。只做前一半，`window.` 归零了 `import frontend.gui.Window` 还在，端口等于白抽。

#### 出站端口

```java
interface AgentSink {
    void setGenerating(String sessionId, boolean generating);
    AiWriter appendAi(String sessionId, String messageId);           // 句柄负责增量与收尾
    ToolWriter appendToolCall(String sessionId, String messageId, String toolName, String callId);
    void appendUser(String sessionId, String messageId);             // 外部注入的用户消息
    void usage(String sessionId, UsageView usage);                   // 用量胶囊
    void notify(String sessionId, NoticeLevel level, String text);   // sessionId 可空
    Boolean requestApproval(String sessionId, String messageId, String callId,
                            ApprovalPayload payload, boolean additionalRequest,
                            long deadlineEpochMs);                   // null = 无前端
    boolean onBackgroundDone(String sessionId, String callId, String output);
    void onBackgroundKilled(String sessionId, String callId);
}

interface AiWriter {
    void chunk(String text);
    void thinking(String text);
    void finishThinking();
    void finish();
}

interface ToolWriter {
    void args(String delta);                                        // 参数增量，只展示不落库
    void executing();                                               // 进入执行阶段
    void finish(String result, boolean success, String arguments);   // 终态：结果落库、卡片翻转
}
```

九个方法的形状都不是随手定的，每一处都对应现在被 `Window` 私有类型挡住的能力：

| 端口设计 | 对应现状 |
|---|---|
| `appendAi` 返回 `AiWriter` 而不是 void | AI 侧有三个出口：`stream.appendChunk`、`stream.finish`、`stream.appendThinking` + `finishThinking`。返回 void 的端口接上就是**断流**——正文无处可去 |
| `appendToolCall` 返回 `ToolWriter` 而不是 void | 工具侧同理。`Window.ToolCallHandle` 四个方法 `Main` 全用了：`appendArgs`（`:453`）、`markExecuting`（`:467`）、`requestApproval`（`:571`）、`finish`（`:652`）。只给 sink 级的阻塞审批不够——参数增量不显示、执行阶段标记丢失、**终态结果无处回填**（`finish` 是唯一把结果落库并翻卡的入口）。AI 侧补了 `AiWriter` 而工具侧仍是 void，等于同一种错误换了个位置 |
| `appendToolCall` 不带 `argsSummary` | 主链调用恒传 `""`（`Main:625`），参数实际来自 `FunctionToolCallDeltaEvent` 的增量。端口照抄了一个永远为空的入参；初态由 `MessageAppended` 带 `ToolState.RUNNING`，终态参数随 `finish` 走 |
| 两个 append 都带 `messageId` | `addAiMessage` / `addToolCall` 现在靠返回 `Window.AiStream` / `Window.ToolCallHandle` 句柄寻址，句柄里裹着 `Message` 对象。端口不能返回窗口类型，用 `messageId` 才能让后续 `ToolStateChanged` 对上是哪张卡 |
| `requestApproval` 带 `sessionId` + `messageId` | 多会话同开时审批要路由到正确的会话与卡片，现有实现靠 `callIdHandleMap` 全局查表（`Main:561`） |
| `requestApproval` 带 `additionalRequest` | `ToolApprovalGate.allow(toolCall, additionalRequest)` 有两个形参；`additionalRequest` 表示"读工作区外"的额外确认，`FULL_ACCESS` 下这条路径直接放行。丢了它，额外确认语义消失 |
| `requestApproval` 带 `deadlineEpochMs` | `ToolApprovalGate` 本身无超时，是现有实现在 `while (!cancelled.get())` 里每 200ms 轮询。端口不给 deadline，核心就没有能力在超时后收回等待，8.8 那句"必须填"只能是装饰 |
| `onBackgroundDone` 返回 boolean | 调用方用它决定要不要续一轮（抢到锁才起新链）。返回 void 就只能瞎猜，后台结果回来后续不续轮无据可依 |
| `usage` 带 `sessionId` | 现在靠 `convId.equals(getStore().getActive().getId())` 判断"是否显示中"再刷胶囊（`Main:539`）——核心在猜前端在看哪个会话。带上 id，由前端自己判断 |

**端口的每个方法都必须有事件接班，才允许退役。** 这是第 4 步能不能删端口的唯一判据：

| 端口方法 | 第 4 步后由谁接管 |
|---|---|
| `setGenerating` | `SessionStatus`（链级，由 `RoundStarted` / `RoundFinished` 推导，见第六节） |
| `appendAi` | `MessageAppended` + `MessageDelta` + `MessageCompleted` |
| `appendToolCall` | `MessageAppended`（带 `ToolState.RUNNING`）+ `ToolStateChanged` |
| `appendUser` | `MessageAppended` |
| `usage` | `RoundFinished.usage` |
| `notify` | `Notice` |
| `requestApproval` | `HostRequestOpened` / `HostRequestClosed` |
| `onBackgroundDone` | `ToolStateChanged(BG_DONE)` + `RoundStarted(BACKGROUND)` |
| `onBackgroundKilled` | `ToolStateChanged(BG_KILLED)` |

**`Notice` 因此必须落在第 4 步，不能拖到第 5 步。** `notify` 承载三处错误提示（启动失败、流式错误、流式异常），第 4 步删端口时若 `Notice` 还没到，验收项"能连续跑 3 轮"在出错时会完全静默。其余方法都有现成接班者。

四类东西**不进端口**：

- `getStore()`：4.2 搬完后核心自己持有状态树，没有"向窗口要 store"这回事。
- `getSelectedEffort` / `getSelectedMode`：旧会话回落到输入区当前选中的值，那是展示态（8.11），无头模式下也没人可问。回落值改由核心的默认配置提供，见 7.6。
- `setRealtimeInfo`：停止时的"正在等待工具收尾…"，前端自己知道刚调了 `cancel()`、也知道 `RoundCancelled` 什么时候来，本地显示即可，不必过一次核心往返。
- `setVisible`：窗口生命周期归组合根。

#### 入站方向与组合根

`main()` 要拆成两个：`CoreMain`（无窗口，持有核心与端口装配）与 `SwingApp`（`new Window`、`setVisible`、注册回调、实现 `AgentSink` 与后台任务控制接口）。

入站回调不能带 UI 类型，也不能让核心靠"当前会话"这个隐式状态去猜：

| 现状 | 改成 |
|---|---|
| `onInputSubmitted(conversation, text)` 传会话对象 | `submit(sessionId, clientMsgId, text)` |
| `onRegenerate(conversation)` | `regenerate(sessionId, fromMessageId)` |
| `onStopRequested(() -> …)` 内部 `getStore().getActive()` 猜当前会话 | `cancel(sessionId)`，由前端指名 |
| `setBackGroundTaskControl(Window.BackGroundTaskControl)` | 核心定义 `BackgroundTaskControl`（`kill` / `output`），Swing 实现；否则这个类型继续从 UI 指回核心 |

`onStopRequested` 那一处最典型：核心现在靠 `getActive()` 猜"用户想停哪个会话"，两个前端同开时会停错。改成显式 id，8.11"当前会话归前端"才真正成立。

**端口按 `messageId` 寻址，因此 4.3 必须先于 4.1。** 现有代码里 `conversationId` 就够用，是因为消息只有一个隐式的"末尾"位置；一旦并行会话、分叉、后台回填同时存在，必须能指名到具体一条消息。

**`AgentSink` 是过渡件。** 它只承担第 2 步的职责：把 agent 链从 UI 上摘下来。第 4 步起由投影层发布事件，Swing 退化为普通订阅者，端口随之删除。退役的条件见上面的映射表——不是"第 4 步到了"，是"每个方法都有事件接班"。不写死这条，后续会同时维护"端口"和"事件"两套出口，`notify` 与 `Notice` 就是同一个通知的两个来源，正好踩中 11.3 的反例。

完成判据：**`Main` 中不再出现 `import io.github.preschoolller.agentjava.frontend.gui`。** 只看 `window.` 归零不够——`Window.AiStream` / `Window.ToolCallHandle` 现在还出现在 16 行方法签名与局部变量上（`:229,262,264,394,405,409,444,455,552,561,599,607,615,622,625,635`），`window.` 没了而 import 还在，编译期依旧依赖窗口类型。同理 `SwingUtilities.` 必须归零（现存 24 处），EDT 编排全部收进 Swing 侧。

### 4.2 状态树必须搬出 `frontend`

`ConversationStore`（586 行，含 `Files.writeString` / `Path` / `ATOMIC_MOVE`）、`Conversation`、`Message`、`AppSettings`（917 行，含 `Properties` 落盘）全部在 `io.github.preschoolller.agentjava.frontend.store`。

也就是说：现在的"前端"是状态与持久化的所有者，"后端"（`Main`）反过来依赖前端。目标架构要求完全相反——核心持有状态，前端只是渲染器。

改造方式：这四个类搬到与 UI 无关的 core 包，持久化留在 core 内部（本层不暴露任何文件概念，见 10.3）。搬完后 `frontend` 只剩渲染与事件订阅。

**搬家的同时摘掉 `activeId`。** 它是"哪个会话正在显示"，属于前端私有（8.11）。`ConversationStore` 里两个方法靠它工作，必须一起拆：

- `getActive()` 在仓库为空时会自动建一个会话——一个查询带写副作用；
- `switchTo()` 在离开空会话时把它连文件一起删掉——没有"离开"这个信号就无从触发。

改成显式传 id 的命令，见 7.3 的 `createSession(workspace, reuseIfEmptySessionId)` / `deleteSessionIfEmpty`，以及 8.15。

**为什么搬家排在加 id 之前**：两步动的是同一批文件和同一段落盘兼容代码。搬家只改包名与 import，是纯机械的一步；加 id 要动序列化格式并写兼容读取，是真正的语义变更。先搬家，后面的回归就只需二分一次语义变更；反过来则路径与格式混在一起，出问题分不清是哪一半。

4.2 与 4.3 相互独立，可以并行；4.1 依赖 4.3（端口按 `messageId` 寻址），但不依赖 4.2。三者都排在本层接口的实现之前。

### 4.3 消息需要稳定标识

`Message` 是 8 字段 record，**没有 id**，更新靠传对象引用。事件流必须能寻址"哪条消息变了"；对象引用跨不了进程，也跨不了语言；后台回填与前台流式并发更新同一条消息时，引用语义更脆弱。前端要做按键增量更新（React 的 key、TUI 的行缓存），也需要一眼能认的稳定 key。

`ConversationStore` 里更新已存在消息的方法共 6 个，定位方式分两类：

| 方法 | 定位方式 | 改 `messageId` |
|---|---|---|
| `updateMessageText(id, target, text)` | 对象引用 | 是 |
| `updateMessageContent(id, target, text, thinking)` | 对象引用 | 是 |
| `completeToolCall(id, target, result, success, arguments)` | 对象引用 | 是 |
| `fork(id, target)` | 对象引用 | 是（入参改 `fromMessageId`） |
| `completeBackGroundTask(id, callId, output)` | `callId` | 否——后台回调线程只有 `callId` |
| `terminateBackGroundTask(id, callId)` | `callId` | 否——同上 |

`Conversation` 内部还有 5 个同名方法，其中前三个（`updateMessageText` / `updateToolResult` / `updateMessageContent`）要跟着改成按 `messageId`，后两个（`updateBackGroundResult` / `updateBackGroundKilled`）按 `callId`，保持不动。

**两个按 `callId` 的方法不动，但事件里必须给 `messageId`。** `callId` 是外部句柄（后台回调线程只拿得到它），`messageId` 是状态树里的地址，两者由核心维护一张索引对应。契约写明：`ToolStateChanged` 两个都给，前端以 `messageId` 为准寻址渲染，`callId` 只用来挂审批与终止入口（`HostRequestOpened` / `BackgroundTaskControl`）。不写这句，前端会试图拿 `callId` 当渲染 key，而后台续轮的卡片与前台流式的卡片 id 规则不同。

**`fork` 的 id 语义必须同时定下来**：`Conversation.fork` 用 `message.copy()` 复制前缀，`copy()` 原样复制全部字段，分叉会话会复制出一批与源会话**完全相同的 `messageId`**。

契约取"**id 只在会话内唯一**"，跨会话重复是合法的：

- 前端的渲染 key 用 `(sessionId, messageId)` 复合，而不是单独的 `messageId`
- 分叉前后"同一条历史消息"保持可关联，便于做对比与溯源

另一种做法是 `copy()` 重新发号，代价是分叉前后失去关联，且多一次 UUID 开销，不取。

落盘格式：`Message` 现按 role 字符串序列化，加 id 需处理旧文件兼容（读时补 id，或一次性迁移）。这是整层成本最高的一处改造，工作量大于接口定义本身。

### 4.4 读取全量的实现约束

`Conversation.getMessages()` 已经调用 `ensureLoaded()`，首次触达自动读盘补齐；`isKnownEmpty()` 只对已加载的会话判空。

因此这里**没有存量改造**，只有一条新代码的硬约束：**投影实现禁止直接读 `messages` 字段，必须经 `getMessages()`**。绕过去就会把懒加载的空壳当成"空会话"投影出去。

## 五、四种流量

| 方向 | 流量 | 内容 |
|---|---|---|
| 前端 → 核心 | 意图 | 提交、取消、改配置 |
| 核心 → 前端 | 状态增量 | 带 `seq` 的事件流 |
| 核心 → 前端 | 宿主请求 | 需要前端应答才能继续（审批、补充输入） |
| 前端 → 核心 | 应答 | 按 `requestId` 配对 |

前两种是常规单向数据流。后两种是**反向交互**，无法并入事件流：它不是通知，是等待应答的请求。三种前端的弹窗形态完全不同（Swing 模态框、TUI 确认行、JS 卡片），若抽象层把它做成回调 `Supplier<Boolean>`，三边都要各自实现弹窗生命周期。

宿主请求必须是**推送**的，不能只给一个查询口：`HostRequestOpened` / `HostRequestClosed` 走事件流，`pending()` 只承担"补拿"（前端重连或重启后取回未答请求）。否则前端只能轮询才能发现审批，而轮询在第十一节里是明确的反例。

## 六、投影类型

纯数据，无持久化、无 UI 类型。前端的全部渲染输入来自这里。

```java
record Snapshot(long seq, List<SessionSummary> sessions) {}

record SessionSummary(String id, String title, boolean pinned, String workspace,
                      SessionStatus status, long updatedAt) {}

record SessionView(String id, String title, String workspace, SessionStatus status,
                   String modelName, String modelProfile,
                   ReasoningEffort effort, AgentMode mode,
                   UsageView usage, List<MessageView> messages) {}

record MessageView(String messageId, String clientMsgId, Role role, String text,
                   String thinking, long time, MessageState state, ToolView tool) {}

record ToolView(String callId, String name, String argsSummary, ToolState state,
                boolean truncated) {}

record UsageView(long inputTokens, long outputTokens, double elapsedSeconds) {}

enum SessionStatus { IDLE, RUNNING }

enum MessageState { PENDING, CONFIRMED, REJECTED, CANCELLED, FAILED }

enum Role { USER, ASSISTANT, TOOL_RESULT }

enum ToolState { RUNNING, OK, ERROR, INTERRUPTED, BG_RUNNING, BG_DONE, BG_KILLED }

enum ReasoningEffort { NO, LOW, MEDIUM, HIGH, ULTRA, ON, OFF }

enum AgentMode { PLAN, EDIT, FULL_ACCESS, CHAT }
```

几条硬性规定：

- `ReasoningEffort` / `AgentMode` 是本层自己的枚举，取值与 `spi.enums` 的同名枚举一一对应，映射写在投影实现里。前端不该 import `spi`——它需要的是取值域，不是插件契约。
- `Role` 同样定义在本层（`USER` / `ASSISTANT` / `TOOL_RESULT`），映射写在投影实现里。现有消息的 role 是字符串常量，另有 `context-manager` 一种水位线标记——它在投影时被过滤掉，所以连枚举值都不必要。**前端一律不 import `spi`**，这条对 `Role` 和 `ReasoningEffort` 一样成立；"复用 spi 枚举"与"前端不碰 spi"不能同时成立，取前者就得放弃后者。
- `ToolState` 与现有落盘字符串一一对应：`running` / `ok` / `error` / `interrupted` / `bg-running` / `bg-done` / `bg-killed`。**"等待审批"不是工具状态**，由 `HostRequestOpened(kind = TOOL_APPROVAL, callId)` 派生。单列一个状态会造出两套真相：卡片在等审批，状态字段却已流转。
- `ToolView.truncated` 与 `ToolStateChanged.truncated` 是同一份数据：工具结果被截断时为 `true`，前端据此显示"仅显示前 N 行"。截断策略本身挂在决策 13，落地前恒为 `false`——但不能省掉字段，否则前端无法区分"输出就这么长"和"只给了这么多"。
- `SessionView.effort` / `mode` 是**生效值**，不是存储值：会话上没盖过戳时由投影解析成 `RuntimeConfig.defaultEffort()` / `defaultMode()`，所以这两个字段非空。前端一律按它渲染输入区选中项——若前端自己保留"上一次的选择"，就会出现"用户看到 HIGH、实际发出 MEDIUM"。
- `SessionStatus` 是**链级**的，不是轮级：`RUNNING` 从该链第一个 `RoundStarted` 起，到 `RoundFinished(chainEnded = true)` / `RoundFailed` / `RoundCancelled` 任一出现为止。按轮推导会在每轮之间闪一下 `IDLE`，而 `setConversationGenerating` 本来就是链级开关（每轮开头置 true，链收束时统一置 false）。
- `MessageView` 的两个 id 是乐观更新的全部成本：`messageId` 由核心给，`clientMsgId` 由前端给。
- `Snapshot` **不含"当前会话"**。哪个会话正在显示是前端的私有状态，见 8.11。

### 7.3 命令

```java
interface AppCommands {
    // 会话
    CreateSessionResult createSession(String workspace, String reuseIfEmptySessionId); // null = 永不复用
    String ensureSession(String sessionId, String workspace);
    void renameSession(String sessionId, String title);
    void pinSession(String sessionId, boolean pinned);
    void deleteSession(String sessionId);
    void deleteSessionIfEmpty(String sessionId);      // 前端切走时调，幂等
    String forkSession(String sessionId, String fromMessageId);

    // 对话，全部异步、立即返回
    void submit(String sessionId, String clientMsgId, String text);
    void regenerate(String sessionId, String fromMessageId);
    void cancel(String sessionId);

    // 会话级配置
    void setWorkspace(String sessionId, String workspace);
    void setModel(String sessionId, String profileName, String modelName);
    void setReasoningEffort(String sessionId, ReasoningEffort effort);   // null = 回落全局默认
    void setAgentMode(String sessionId, AgentMode mode);                 // null = 同上
}

record CreateSessionResult(String sessionId, boolean reused) {}
```

- `ensureSession`：面向"外部已持有会话 id"的场景，语义为幂等 upsert；已存在则复用且不改 workspace，`workspace` 仅新建时生效。
- `createSession` 的第二个参数是**前端正在显示的那个会话 id**，可为 null。非 null 且该会话存在、且为空会话时，复用它并改 workspace，`reused = true`，返回的**不是新 id**；null 表示必定新建。核心不再靠"当前会话"这个隐式状态去猜，见 8.15。
- `deleteSessionIfEmpty`：空会话则删掉（含落盘），非空则什么都不做。这是"切走时清理空会话"那条产品行为的显式化——前端在自己的切换处调用；不想保留这条行为的前端干脆不调，代价是攒空会话。
- **没有 `selectSession`。** 切会话是前端换一个 `session(id)` 去渲染，不需要通知核心。
- `deleteSession` / `forkSession` 不返回"建议切到哪个"：删完前端从 `snapshot()` 里自己挑（顺序见 8.18），分叉的新 id 本身就是返回值，跟不跟由前端决定。核心不再持有"当前"，也就没有"下一个当前"可推荐。
- 四个会话级 setter 都必须发 `ConfigChanged`（`sessionId` 非空），与 `RuntimeConfig` 的全局 setter 同一规则，见 8.12。`setReasoningEffort(sessionId, null)` / `setAgentMode(sessionId, null)` 表示清除该会话的盖戳、回到 `defaultEffort` / `defaultMode`，与 `setEnabledTools(null)` 同一约定。
- `submit` 在会话忙时的行为见 8.14。

### 7.4 事件

全部事件实现同一个根类型，便于一处订阅、一处分发。

```java
sealed interface StateEvent
        permits SessionCreated, SessionRemoved, SessionRenamed, SessionPinned,
                MessageAppended, MessageDelta, MessageCompleted, ToolStateChanged,
                UserMessageConfirmed, UserMessageRejected,
                RoundStarted, RoundFinished, RoundFailed, RoundCancelled,
                HostRequestOpened, HostRequestClosed, ConfigChanged, Notice, GapDetected {
    long seq();

    /** 不绑定会话的事件（全局配置变更、流级控制信号）返回 null */
    default String sessionId() { return null; }
}

record SessionCreated(String sessionId, SessionSummary summary, long seq)        implements StateEvent {}
record SessionRemoved(String sessionId, long seq)                                implements StateEvent {}
record SessionRenamed(String sessionId, String title, long seq)                  implements StateEvent {}
record SessionPinned(String sessionId, boolean pinned, long seq)                 implements StateEvent {}

record MessageAppended(String sessionId, MessageView message, long seq)          implements StateEvent {}
record MessageDelta(String sessionId, String messageId,
                    String textDelta, String thinkingDelta, long seq)            implements StateEvent {}
record MessageCompleted(String sessionId, String messageId, long seq)            implements StateEvent {}
record ToolStateChanged(String sessionId, String messageId, String callId, ToolState state,
                        String resultText, boolean truncated, long seq)           implements StateEvent {}

record UserMessageConfirmed(String sessionId, String clientMsgId,
                            String messageId, long seq)                          implements StateEvent {}
record UserMessageRejected(String sessionId, String clientMsgId,
                           String reason, long seq)                              implements StateEvent {}

record RoundStarted(String sessionId, RoundCause cause, long seq)                implements StateEvent {}
record RoundFinished(String sessionId, UsageView usage, boolean chainEnded, long seq) implements StateEvent {}
record RoundFailed(String sessionId, String reason, long seq)                    implements StateEvent {}
record RoundCancelled(String sessionId, long seq)                                implements StateEvent {}

record HostRequestOpened(String sessionId, Request request, long seq)            implements StateEvent {}
record HostRequestClosed(String requestId, String sessionId,
                         CloseReason reason, long seq)                           implements StateEvent {}

record ConfigChanged(String key, String sessionId, long seq)                     implements StateEvent {}
record Notice(String sessionId, NoticeLevel level, String text, long seq)        implements StateEvent {}

record GapDetected(long sinceSeq, long earliestSeq, long seq)                    implements StateEvent {}
// GapDetected 是流级控制信号，sessionId() 恒为 null，由 StateEvent 的默认实现提供；收到后重拉快照并丢弃本地增量，见 8.2

enum RoundCause { SUBMIT, BACKGROUND }

enum CloseReason { ANSWERED, TIMEOUT, AUTO_REJECTED, CANCELLED }

enum NoticeLevel { INFO, WARN, ERROR }
```

`sessionId()` 声明为 `default` 返回 null，是为了让"不绑会话"的事件不必各自写一遍空实现——record 只要带了 `sessionId` 分量，生成的访问器就自动覆盖默认方法；不带分量的（`GapDetected`）直接继承 null。v0.3 的 `GapDetected` 就是漏了这点，空体实现不了接口方法。

几点必须写进契约：

- `RoundStarted.cause`：`BACKGROUND` 表示后台任务完成在空闲会话上**自行起了一条新链**，不经过任何 `submit`。前端若按"submit 后才有轮次"建模会错。
- 后台任务完成**不单列事件**：卡片终态与输出走 `ToolStateChanged(state = BG_DONE, resultText)`，随后若续了一轮就是 `RoundStarted(cause = BACKGROUND)`。专门再造一个 `BackgroundTaskFinished`，等于同一件事有两个来源，谁先到谁后到都得约定。
- `RoundFinished.chainEnded`：`false` 表示工具结果还要续下一轮，`true` 表示整条链收束。一次带 3 个工具调用的对话会发 3 组 `RoundStarted/RoundFinished`，前端只看"收到 RoundFinished 就算结束"会把中间轮当成终点。`RoundFailed` / `RoundCancelled` 恒为链终态。
- `MessageCompleted` 只是收束信号，不带最终正文。正文以 `MessageDelta` 累积为准；若前端漏了 delta（重连、被截断），应重拉 `session(id)` 而不是把空串当结果。
- **工具消息的终态正文走 `ToolStateChanged.resultText`**，不走 `MessageDelta`（工具结果一次性落库，没有增量）。这个字段不能省：`MessageCompleted` 不带正文，若 `ToolStateChanged` 只给摘要，前端拿到一个 bash 任务的完成通知后手里只有摘要，要看全文只能重拉会话。
- `MessageDelta` 需由核心**按帧合并**后推送。逐 token 直推会压垮终端刷新，也会把 HTTP 打成大量小包。
- `ConfigChanged.sessionId` 为 null 表示全局配置项变化（方案、MCP 名单、启用工具），非 null 表示会话级配置。
- `ConfigChanged` **不带新值**，只是"这项变了"的信号。前端收到后必须重拉对应查询（会话级 → `session(id)`，全局 → `profiles()` / `enabledTools()` 等）。契约里不写这句，JS 侧会等一个永远不来的字段。
- `Notice` 覆盖"链还没开始就失败"这一类：`RoundFailed` 只管一轮，启动链路异常、上下文构建失败发生在轮之前，落不到任何一个轮事件上。`sessionId` 可空（全局错误）。
- `HostRequestClosed.reason`：`ANSWERED`（前端作答）、`TIMEOUT`（到达 `deadlineEpochMs`）、`AUTO_REJECTED`（无前端或卡片已失效，见 8.8）、`CANCELLED`（会话被取消或请求作废）。无头运行时的自动拒绝靠它留痕。

### 7.5 审批

```java
interface HostRequests {
    sealed interface Answer permits Approve, Reject, TextAnswer {}
    record Approve()             implements Answer {}
    record Reject(String reason) implements Answer {}
    record TextAnswer(String value) implements Answer {}

    sealed interface Payload permits ApprovalPayload, InputPayload, ConfirmPayload {}
    record ApprovalPayload(String toolName, String argsSummary, String argsRaw) implements Payload {}
    record InputPayload(String prompt, String defaultValue) implements Payload {}
    record ConfirmPayload(String title, String detail) implements Payload {}

    record Request(String requestId, String sessionId, String callId,
                   Kind kind, Payload payload, long deadlineEpochMs) {}

    enum Kind { TOOL_APPROVAL, USER_INPUT, CONFIRM }

    List<Request> pending();
    void answer(String requestId, Answer answer);
    void cancel(String requestId);
}
```

- 三种应答形态分开，避免"传一半参数是废值"的万能签名。
- `callId` 可空（`USER_INPUT` / `CONFIRM` 没有工具卡），非空时前端据此把应答挂到具体那张卡上，不需要解析 `payload`。
- `payload` 按 `Kind` 拆成三个结构化 record，`kind` 与 payload 类型必须一一对应。
- `deadlineEpochMs` 是硬截止，必须填。到点后核心自行按决策 5 的基线动作收尾（当前是拒绝）并发 `HostRequestClosed(TIMEOUT)`。同一条约束要落到阻塞侧：`AgentSink.requestApproval` 带同一个值，实现方负责让阻塞调用在到点时返回——否则核心里那个等待线程没有任何手段收回，字段就是装饰。
- `pending()` 是**补拿**口，不是发现口，见第五节。前端重启后靠它取回未答请求，否则正在等审批的会话会静默挂死。取回时若已过截止时间，按 `TIMEOUT` 处理，不要试图作答。

四条与现有代码直接相关的约束：

1. **没有 `activeProfile`。** `AppSettings` 刻意没有"活动方案"概念：用哪套配置由会话选中的模型所属方案决定，路由走 `Conversation.modelProfile` + `findProfileOwningModel` 反查。再加一个 `setActiveProfile` 会造出第二个真相源。方案选择已经在会话级的 `setModel(sessionId, profileName, modelName)` 上承载。
2. **`defaultWorkspace` 只读。** 它是 `AppSettings.defaultWorkspace()` 里的静态常量，没有落盘键也没有 setter。要让它可改，得先新增一个持久化配置项（见决策 10），不能顺手在接口上加个 setter 就当实现了。
3. **`enabledTools` 必须是三态。** `null` = 从未配置（全部启用，含将来新增的工具）、空列表 = 显式全不启用、列表 = 部分启用。压成一个 `List<String>` 会丢掉 `null` 与空列表的区别，前端就无法表达"恢复默认"。
4. **`toolProperty` 必须带命名空间。** `AppSettings.toolProperties` 里实际只有 `plugin-properties.<插件名>` 一种键，插件持久化输入用的是同一张表。本层的 key 定为 `tool.<toolId>.<key>`，并且契约禁止前端读写 `plugin-` 前缀。

## 八、契约中必须明确的细节

这一节决定三种前端能否写出同一套逻辑。每条都标了不照做的后果。

### 8.1 快照与 seq 的原子性

`Snapshot` 携带 `seq`，订阅从该 seq 起消费。**取快照与打 seq 必须在同一临界区内完成。**

若拆成"先 `sessions()` 拿全量，再 `subscribe(sinceSeq)`"，两步之间的事件会永久丢失：拿到旧列表、错过中间变更、新 seq 已越过那段区间。

替代方案是"先订阅再取快照"（用快照覆盖本地并丢弃快照前事件），对核心压力更小，但前端要去重。采用前者，实现时不要图省事拆开。

### 8.2 订阅的缓存与缺口

`sinceSeq` 决定了订阅必须能重放历史事件，否则这个参数没有意义。实现约束：

- 核心维护环形缓冲（容量 N，N 由决策 12 定），保留最近 N 条事件
- `sinceSeq` 早于缓冲起点时，立即回一条 `GapDetected`，前端重拉 `snapshot()` + 当前会话的 `session(id)`，并丢弃本地增量
- 慢消费者不静默丢弃：超限即按缺口处理，宁可重拉也不能让前端静默落后

缺口必须是一个**显式信号**。缺了它，前端会在重连后安静地显示一份过期状态，而且没有任何一处会报错。`GapDetected` 因此是事件流里的**控制信号，不是状态变更**：它不属于任何会话（`sessionId()` 为 null），带 `earliestSeq` 供前端判断落后多少；收到后一律重拉快照、丢弃本地增量，不做增量重放。

### 8.3 消息文本的归属

`submit` 后前端本地先插一条 `PENDING` 空消息，核心也会 append 一条。**这条 `MessageAppended` 里的 `text` 是空还是全文，必须写进契约。**

规则：

- `USER`：append 时带全文，无 delta。用户消息内容不会变。
- `ASSISTANT`：append 时 `text` 为空，内容只从 `MessageDelta` 累积。
- `TOOL_RESULT`：append 时 `text` 为空，终态由 `ToolStateChanged.resultText` 推送；**快照里 `MessageView.text` 是同一份数据**——现有落盘就是"工具消息的 `text` 存工具结果"，投影照搬即可。只重连、不重放事件的前端靠这一条才拿得到全文；不写明就会有人按"`text` 只给聊天消息"实现，工具卡永远是空的。截断与否看 `ToolView.truncated`。
- `CONTEXT_MARKER`：投影时过滤掉，不出现在 `MessageView` 里（见第六节的 `Role`）。

不统一则前端会重复计入正文，或者渲染一条永远空着的消息。

### 8.4 乐观更新的配对与孤儿

前端生成 `clientMsgId` 渲染 PENDING，核心回 `UserMessageConfirmed(clientMsgId, messageId)` 配对转正，或 `UserMessageRejected` 标记失败。

**孤儿问题**：前端崩溃后，核心那边那条 PENDING 永远等不到配对（`clientMsgId` 随进程消失）。

处理规则（择一，实现前定）：

- 核心不持久化 PENDING，收到确认才落盘 —— 语义最干净（没确认即未发生），要求 append 的落盘时机与确认对齐
- 先落盘，启动时扫描清理为 `REJECTED`
- 前端把 PENDING 视作请求级事务，超时自动回滚

### 8.5 消息状态的取值边界

五态，语义需逐条写清，否则前端只能把它们都当灰色处理：

| 状态 | 含义 |
|---|---|
| `PENDING` | 前端已乐观插入，核心尚未确认 |
| `CONFIRMED` | 已确认并落盘的正常消息 |
| `REJECTED` | 提交被拒（会话不存在、参数非法、显式拒绝策略），不会进入上下文 |
| `CANCELLED` | 所在轮次被取消时的半截消息，保留但不可继续 |
| `FAILED` | 流式中途失败 |

**没有"已作废"态。** `regenerate` 的语义是截断到指定点并重跑（与现有 `removeLastMessage` 一致），旧消息已被移除，不存在需要标记作废的记录。若将来改成"保留并标记作废"，必须同时回答"作废消息是否进上下文"，那会连带影响决策 4。

**工具消息的状态归属**：同一条 `MessageView` 上并排两个状态维度（`state` 与 `tool.state`），必须规定谁说了算。规则是：

- 工具消息的 `state` 恒为 `CONFIRMED`；其所在链被取消时，**只有还没到终态的（即 `ToolState.RUNNING`）**翻成 `CANCELLED`，已经 `OK` / `ERROR` / `BG_*` 的不动
- 工具的执行生命周期**只看 `ToolState`**，前端不为工具消息写 `state` 分支

取消只回溯"还没结束的"，是因为已经跑完的工具不会因为用户按了停止而变成没跑过；若把整条链上的工具消息一律改写，取消就成了一次对历史结果的重写，还得给核心加一趟扫描。

不规定的话，前端要维护一张两维状态的真值表，而且 `running` + `FAILED` 这种组合会出现两种解释。

### 8.6 取消语义

`cancel` 幂等：对已结束的会话调用不应报错，也不应产生第二条 `RoundCancelled`。

**`cancel` 只置取消意图并立即返回，`RoundCancelled` 在链真正收束时发出。** 两者可能相隔很久：已派发的工具还要 `join` 等它落地（最长等到工具执行超时）。前端不能把 `cancel()` 的返回当成"已停止"，状态翻转以事件为准。

取消后已产生的半截内容保留还是删除，与上下文是否包含它绑定，见决策 4。

### 8.7 为什么没有 editMessage

"改一条历史消息"在 agent 上下文里等于"截断到该点并重跑"，与 `regenerate` 是同一动作。拆成两个方法，前端要么只用其中一个（另一个是死方法），要么两个都调（重跑两次）。因此只保留 `regenerate(sessionId, fromMessageId)`。

### 8.8 审批的三条既有路径与无头默认动作

`ToolApprovalGate` 的契约是「实现可以阻塞等待用户点击」，`boolean allow(...)` 无超时，在工具执行线程上同步阻塞。现有实现有三条路径（`Main.requestToolApproval`）：

| 情形 | 行为 |
|---|---|
| 有工具卡且未取消 | 每 200ms 醒一次等点击，阻塞至用户作答 |
| **无工具卡**（含无头模式） | **立即返回拒绝** |
| 用户已停止本轮 | 立即返回拒绝 |

所以无头模式不会挂死，而是"**静默拒绝所有需审批的工具**"。这比挂死更难排查：跑完一轮得到的是一段工具全都不执行的对话，没有任何错误信号。

契约要求：

- `Request.deadlineEpochMs` 必须填，超时后的动作由决策 5 定；基线选项是"保持自动拒绝"。这个值同时交给 `AgentSink.requestApproval`，由实现方保证阻塞调用在到点时返回——只写在 `Request` 上，核心那个等待线程没法自己醒来。
- 无前端时的默认动作必须在 `HostRequests` 上显式声明，不能依赖"恰好没有卡片"这个隐式条件
- 每次自动拒绝都要留痕：`HostRequestClosed(reason = AUTO_REJECTED)`（超时为 `TIMEOUT`）。没有这条，无头跑一轮得到的是"工具全都不执行"的对话，日志里也找不到解释

### 8.9 工具状态的枚举与等待审批的归属

`ToolState` 七个值直接对应落盘字符串，见第六节。等待审批不单列状态：审批是挂在工具卡上的**外部请求**，不是工具自身的生命周期阶段。前端收到 `HostRequestOpened(kind=TOOL_APPROVAL, callId)` 时自行给该卡加"待确认"外观，收到 `HostRequestClosed` 后撤掉。

若把它做成 `ToolState.WAITING_APPROVAL`，就会出现"状态已翻到 ok、请求还挂着"或反之的不一致，而且后台任务三态与审批态的组合会把状态机撑成二维。

### 8.10 工具参数的表达

现有 `appendToolCall(id, toolName, argsSummary, callId)` 传的是摘要。摘要用于展示，原文用于脚本前端读取完整参数，一个字段装不下。`ToolView.argsSummary` 只承担展示用途；需要原文时另行设计字段，见决策 7。

**结果这一侧同样要说清。** 工具结果的正文通过 `ToolStateChanged.resultText` 推送，快照里是同一份数据落在 `MessageView.text`（见 8.3）。"被截断"的标志已经定进类型：`ToolStateChanged.truncated` 与 `ToolView.truncated`，前端据此显示"仅显示前 N 行"。截多少、要不要按需拉全文挂在决策 13，落地前该字段恒为 `false`——先留字段是因为加字段比改语义便宜，而一旦真的开始截断却不说，前端只能猜"输出就这么长"还是"只给了这么多"。

### 8.11 前端私有状态不进核心

以下三类是前端私有，**不进投影、不进命令**：

| 私有状态 | 说明 |
|---|---|
| 当前选中会话 | Swing 和 JS 同开时，一个前端切会话不该把另一个拽走 |
| 滚动位置 / 折叠状态 / 视口窗口 | 纯渲染 |
| 输入框草稿、未发送的附件 | 前端本地 |

这与"前端零持久化"不矛盾：**零持久化指跨进程重启不保留，不是运行期无状态**。把"当前选中会话"放进 `Snapshot`、再配一个 `selectSession` 命令，就是把展示态写进了共享状态树——两个前端同开时会互相拽动，和"未读归属"属于同一类错误。

### 8.12 配置变更事件

**所有 setter 都要产生 `ConfigChanged`，不只 `RuntimeConfig` 上的那些。** 这包括 `AppCommands` 里的四个会话级 setter（`setWorkspace` / `setModel` / `setReasoningEffort` / `setAgentMode`）——它们改的是"两个前端同看一个会话"时会被同时看到的属性。按字面把范围限定在 `RuntimeConfig` 上，一侧改了模型另一侧就永远不知道，正是本条要避免的问题。会话级变更的事件带非空 `sessionId`，全局项为 null。

事件**不带新值**，只说明"这一项变了"。收到就重拉：会话级重拉 `session(id)`，全局重拉 `profiles()` / `enabledTools()` / `mcpServers()`。想让事件自带新值得给每种配置项定义载荷类型，收益远小于成本。

### 8.13 未读状态的归属

多会话列表需要显示"哪个会话有动静"。两个前端同开同一会话时，"已读"是全局还是本地，是产品决策：

- 全局：A 读过后 B 不再显示红点，多设备体验差
- 本地：核心不持有该概念，不进 `SessionSummary`

**先定归属，再决定是否进投影类型**，否则会渗进去后难以移除。按 8.11 的划分，倾向本地。

### 8.14 submit 的并发语义

现有实现：抢不到会话锁直接静默 return；外部注入路径先记 `PENDING_BG_DELIVERY` 再抢锁，由链首快照消化。

`submit` 是异步立即返回的，但"会话正忙"时的行为必须明确，三种选择对前端影响完全不同：

| 策略 | 前端后果 |
|---|---|
| 拒绝 | 必须回滚乐观插入的那条 PENDING，并给出提示 |
| 排队 | 需要显示"第 N 位"，且要能取消排队 |
| 并入当轮 | 不需要额外 UI，但语义含糊（消息落在哪一步之后） |

未定之前，默认取**拒绝**并保证 `UserMessageRejected` 一定发出——静默丢弃是最坏的一种，前端会永远挂着一条 PENDING。`UserMessageRejected` 的触发条件收敛为三种：会话不存在、参数非法、显式拒绝策略。

**插件注入路径不参与这条策略。** `AgentJavaSessions.inject`（落点是 `apiInject`）走的是"并入当轮"：消息先落库出卡，再记补偿标记抢锁，抢不到的由在跑的链在下一轮快照里消化，或链尾按标记补一轮。这与前端 `submit` 的拒绝策略**刻意不同**，理由是对外调用方拿不到前端那套 PENDING 回滚，拒绝等于让一次投递无声消失（dsh 侧只会看到 HTTP 200）。两个入口、两种语义，必须写进契约，否则会被当成 bug 修掉。

### 8.15 会话创建与切换的副作用

现有三条行为都靠 `ConversationStore` 里的"当前会话"（`activeId`）工作，而 8.11 把它划给了前端。解法是**把隐式的"当前"换成显式入参**：

| 现有行为 | 代码 | 契约里的形态 |
|---|---|---|
| 创建时若当前是空会话就复用并改 workspace，返回的不是新 id | `ConversationStore:83-101` | `createSession(workspace, reuseIfEmptySessionId)`：第二个参数就是"我正在看哪个"，null = 永不复用 |
| 切走时若离开的是空会话，连落盘一起删 | `:127-136` | `deleteSessionIfEmpty(sessionId)`：前端在自己的切换处调，幂等 |
| 仓库为空时查询会自动建一个会话 | `getActive()`，`:64-79` | 直接禁止。`snapshot()` / `session(id)` 不得走这条路径，空仓库返回空列表 |

不换成显式入参会怎样：`selectSession` 已经删了，核心没有任何途径知道"当前会话"是哪个——"复用空会话"只能恒返回 `reused = false`，"离开时清理"永远不触发。两条产品行为不会报错，只会无声失效，这是最难发现的一类退化。

`activeId` 相应地从共享状态树里删除。各前端在自己的视图层保存"我正在显示哪个"，需要时通过参数传进来（`createSession` / `deleteSessionIfEmpty` / `submit` / `cancel`）。投影里没有它，`Snapshot` 也没有"当前"。

第三条不只是洁癖：`getActive()` 在空仓库上会造一个会话且不发变更事件，`snapshot()` 若走了它，"打开应用看一眼"就变成"凭空多一个会话"。

JS 前端若按"create 必得新 id"或"切走不改数据"建模会直接踩。前两条要不要保留是产品决策，但不写进契约就是陷阱。

### 8.16 消息 id 的作用域

见 4.3：`messageId` 只在会话内唯一，`fork` 复制前缀会产生跨会话重复的 id。前端渲染 key 用 `(sessionId, messageId)`。

### 8.17 失败与通知

`RoundFailed` 只覆盖"这一轮失败"，覆盖不了"链还没开始就失败"（启动链路异常、上下文构建失败）。现有唯一出口是 `window.addNotifyMessage`，三处调用分别在启动失败、流式错误、流式异常。

因此 `Notice(sessionId, level, text, seq)` 是独立事件，已并入 7.4；`sessionId` 可空表示全局错误。它同时是 `AgentSink.notify` 的接班者，**必须落在落地顺序第 4 步**——端口在那一步退役，`Notice` 迟到一步，第 4 步的出错路径就整段静默（见 4.1 的映射表）。

`level` 只影响外观。需要用户应答的提示一律走宿主请求（第五节），不要用 `Notice` 模拟——那样前端只能看着，没法回答。

### 8.18 会话列表的顺序

现有规则是隐式的：`appendMessage` 把会话挪到列表首位，`setPinned` 只改标记不动顺序，侧栏渲染时置顶优先。

写进契约：`Snapshot.sessions` 按 `pinned` 降序、其次 `updatedAt` 降序。`sessionsSince(seq)` 只回变更项、**不保证顺序**，前端自己重排。否则前端要么照抄一份排序规则（两处维护），要么依赖核心的隐含顺序（一旦核心换实现就乱）。

### 8.19 状态所有权

这一层反复出问题的地方不是接口形状，而是"这份状态归谁"：端口归 UI 还是核心、当前会话归前端还是核心、默认值从哪读、工具结果走事件还是快照。逐项定下来，往后加字段先查这张表：

| 状态 | 所有者 | 落点 |
|---|---|---|
| 会话列表、消息正文、工具结果、用量 | 核心 | 投影出去（`Snapshot` / `SessionView`） |
| 会话的 workspace / model / effort / mode | 核心（会话级） | `setXxx(sessionId, …)`；effort / mode 的 null 在投影时解析成生效值 |
| profiles、mcpServers、enabledTools、toolProperties、defaultEffort / defaultMode | 核心（全局） | `RuntimeConfig` |
| 默认工作区 | 核心（只读常量） | `RuntimeConfig.defaultWorkspace()`；要可改先过决策 10 |
| 当前显示哪个会话 | 前端 | 8.11；需要时作为入参传给 `createSession` / `deleteSessionIfEmpty` / `submit` / `cancel` |
| 输入区选中的 effort / mode | 前端只读投影的生效值 | 不作为请求参数的来源，见第六节 |
| 滚动、折叠、视口窗口、草稿 | 前端 | 8.11 |
| 未读标记 | 倾向前端 | 8.13 待定 |
| 审批等待、取消意图、会话锁 | 核心 | 前端只答 `answer(requestId, …)` |
| `clientMsgId → messageId` 配对 | 映射在前端，核心只在 `UserMessageConfirmed` 回传 | 8.4 |
| 窗口生命周期、回调装配、EDT 编排 | 组合根（`SwingApp`） | 4.1 |
| 主题、字号、窗口几何、日志开关 | 前端 / 启动参数 | 7.6 的三类表 |
| PENDING 孤儿清理 | 待决策 8 | 8.4 |

## 十、边界

### 10.1 与插件能力面的区别

| | 插件能力面（`spi`） | 应用抽象层（本文件） |
|---|---|---|
| 调用方 | 同 JVM 内的插件 | 任意前端（进程内 / 跨进程 / 跨语言） |
| 解决的问题 | 插件向宿主借能力（读配置、注册退出钩子、取工具列表、驱动会话） | 前端驱动整个应用（状态从哪来、意图往哪去） |
| 状态 | 无状态，纯转发 | 持有唯一状态树 |
| 形态 | 静态门面 + `install` 注入 | 实例 + 订阅 |

两者在"驱动会话"上有交集，但不合并。合并后插件能看到整套前端状态，前端能看到插件注册能力，两侧都被污染。

### 10.2 禁止出现的类型

方法签名中不允许出现 `Path`、`File`、`Properties`、`java.awt.*`、`javax.swing.*`、`SwingUtilities` 及任何 EDT 相关 API。出现任意一个，说明该处已退化为 Swing 适配器。

### 10.3 不负责持久化实现

本层只回答"状态从哪来"，不回答"存在哪个文件"。持久化是实现细节，藏在投影背后。

### 10.4 包位置

`io.github.preschoolller.agentjava.api` 已被插件会话门面 `AgentJavaSessions` 占用，本层不能放这里，否则两个"api"在 import 上打架。

更重要的是**不能放 `spi`**：放进去插件就能看到整套前端状态，正好违反 10.1。本层应放在 `app` 内部，或独立成 core 模块，且 `spi` 不依赖它。命名建议 `core.app` 或 `application`，与迁移后的状态树同包或同模块。

## 十一、验证

### 11.1 假前端

不依赖真实实现即可判断投影是否够用：写一个 200 行内的 stdout 前端——订阅事件并打印 `MessageView` / delta / 工具状态变化，stdin 读一行生成 `clientMsgId` 后 `submit`，遇宿主请求在终端问 y/n 后 `answer`。能连续跑 3 轮对话、1 次取消、1 次审批即算够用。

写不出来，或需要偷看内部状态才能正确打印，说明状态投影缺东西。这比等第二个真前端写完再发现问题便宜两个数量级。

### 11.2 判据

- 方法名出现"下拉框 / 按钮 / 面板 / 对话框"：抽象到了控件层，退回去重抽
- 某方法只有一种前端会调：它不是本层的东西
- 可枚举的取值用枚举表达，不用 `String` 装（模型名、消息正文这类标识与自由文本除外）
- 流式输出仅靠 apply 增量即可渲染正确：投影与事件完备

### 11.3 反例

出现任一条即说明设计走歪：

- 前端为显示正确需额外调用超过 2 个查询接口
- 需轮询才能知道一轮是否结束，或才能发现有审批请求
- 需在两个接口之间传内部对象引用
- 某前端需访问文件系统才能恢复会话列表
- 同一个状态存在两个来源（例如既有 `activeProfile` 又有会话的 `modelProfile`）

## 十二、落地顺序

| 序 | 内容 | 产出 |
|---|---|---|
| **0** | 状态树搬家：`frontend.store` → core 包，持久化随行，同时摘掉 `activeId` / `getActive()` / `switchTo()`（4.2、8.15） | 无新接口 |
| **1** | 消息稳定 id：4 个按引用改 `messageId` + `fork`，`callId` 两个不动；定下 id 作用域（4.3、8.16） | 改造 |
| **2** | agent 链解耦：出站 `AgentSink`（含 `AiWriter` / `ToolWriter`）+ 入站拆组合根（4.1） | 无新接口 |
| 3 | 快照原子性 + 订阅缓冲与缺口（8.1、8.2）；全量读取降为投影约束（4.4） | 契约落地 |
| 4 | 最小面接口 + stdout 假前端，接进 `mvn test`；`Notice` 必须在此步到位，`AgentSink` 逐方法核对接班者后退役（4.1、8.17） | 首个可验收版本 |
| 5 | 完整面：后台任务的状态与续轮、审批推送、`Request.callId` / `deadlineEpochMs`（8.8、7.5） | 接口补齐 |
| 6 | `RuntimeConfig` 三类拆分 + 方案 CRUD（7.6，CRUD 部分见第十三节） | 配置面 |
| 7 | JS / HTTP 适配器（含长会话分页，见决策 13） | 第二个真实前端 |

**第 0、1、2 步都不产出本层对外的接口，但缺了它们第 4 步无法验收**：`main()` 第一行就是 `new Window(...)`，`apiEnsureSession` / `apiInject` 在窗口为空时直接抛异常。这是整层最容易被低估的成本——重的是前置改造，不是接口数量。

顺序上有两条硬依赖，其余可以调：

- **搬家先于加 id**：两步动同一批文件和同一段落盘代码，先做纯机械的那一步（4.2）。
- **加 id 先于抽端口**：端口按 `messageId` 寻址（4.1），没有 id 就只能继续传窗口句柄，等于没解耦。
