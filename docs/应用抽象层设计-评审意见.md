# 应用抽象层设计 · 评审意见

> 评审对象：《应用抽象层设计》v0.1（commit `c5acfa2`）
> 评审依据：当前 `app` / `spi` 源码（branch `api_use_app`）
> 评审范围：只评审设计与契约本身。未改动 `app/`、`spi/` 任何源码，也未修改原文档。
> 结论：**骨架成立，可以按此方向走**；但有 5 处与代码事实不符、4 处自相矛盾、12 处覆盖缺口，按现状实现会在第二个前端出现时集中返工。

## 总览

| 级别 | 含义 | 条数 |
|---|---|---|
| P0 | 与现有代码事实不符，照做会走错方向 | 5 |
| P1 | 文档内部两处不能同时成立 | 4 |
| P2 | 契约覆盖缺口，实现后才发现补不动 | 12 |
| P3 | 细节与表述 | 6 |

三句话总结：

1. **最硬的前置约束漏了。** 不是消息 id，是 agent 链与 `Window` 的耦合——`Main` 里 23 处 `window.`、24 处 `SwingUtilities.`，`main()` 第一件事就是 `new Window(...)`。不改这条，§12 第 3 步的 stdout 假前端根本启动不了。
2. **目标与包结构对立。** 状态树（`ConversationStore` / `Conversation` / `Message` / `AppSettings`）现在全在 `frontend.store`，且持久化就在同一个类里。"前端零持久化"要求先把这四个类搬到 core，落地顺序里没有这一步。
3. **两条非常规流量各有半截没接上。** 审批只有 `pending()` 拉取口、没有"新请求到来"的推送；后台任务能在空闲会话上自行起新链，投影里却没有任何对应事件。

## 一、P0 与代码事实不符（5 条）

### P0-1 无头模式下审批不会"永久挂死"，而是自动拒绝

**位置**：§8.7（第 323-327 行）、决策 5

**代码**：`Main.requestToolApproval`（`Main.java:551-597`）

```java
Window.ToolCallHandle handle = callIdHandleMap.get(toolCall.getCallId());
if (handle == null || cancelled.get()) {
    LOG.info("审批自动拒绝：handle={} cancelled={}", ...);
    return false;
}
```

`ToolApprovalGate` 确实无超时、在工具执行线程上同步阻塞，但阻塞的实现是每 200ms 醒一次看 `cancelled`（`decision.get(200, MILLISECONDS)`），**没有卡片就立刻返回 false**。无头模式不创建 `ToolCallHandle`，所以行为是"静默拒绝所有需审批的工具"，不是"挂死"。

**影响**：决策 5 的三个选项（自动拒绝 / 自动放行 / 挂起等超时）缺了"保持现状"这个基线。而"静默拒绝"比"挂死"更难排查——无头跑一轮会得到一堆工具不执行的对话，没有任何错误信号。

**建议**：§8.7 改写为三种既有行为并列：有卡片等点击 / 无卡片即拒绝 / 用户停止即拒绝；决策 5 增加"保持自动拒绝"基线，并要求 `HostRequests` 显式声明无头时的默认动作与可审计的拒绝事件。

### P0-2 §4.1 的改造清单：数量与对象都不准

**位置**：§4.1 第 55 行"`ConversationStore` 中 6 个按引用更新的方法改为按 `messageId`"

**代码**：`ConversationStore.java` 里更新已存在消息的方法确实是 6 个，但定位方式分两类：

| 方法 | 定位方式 | 是否该改 `messageId` |
|---|---|---|
| `updateMessageText(id, target, text)` | 对象引用 | 是 |
| `updateMessageContent(id, target, text, thinking)` | 对象引用 | 是 |
| `completeToolCall(id, target, result, success, arguments)` | 对象引用 | 是 |
| `fork(id, target)` | 对象引用 | 是（入参改成 `fromMessageId`） |
| `completeBackGroundTask(id, callId, output)` | `callId` | **否**——后台回调线程只有 `callId` |
| `terminateBackGroundTask(id, callId)` | `callId` | **否**——同上 |

即"4 个按引用 + 2 个按 callId"，不是"6 个按引用"。另外文档只列了 3 个签名，**漏了 `fork`**——而 §7.3 的 `forkSession(sessionId, fromMessageId)` 恰恰要求它改。

**建议**：清单按两类重写，明确"按 `callId` 的两个保持不动"；补 `fork` 与 `Conversation` 内部的 5 个同名方法（`updateMessageText` / `updateToolResult` / `updateMessageContent` / `updateBackGroundResult` / `updateBackGroundKilled`）。

### P0-3 `defaultWorkspace` 不是配置字段，`setDefaultWorkspace` 不存在

**位置**：§7.6 `RuntimeConfig`（第 246 行）、§7.6 三分表第 259 行

**代码**：`AppSettings.java:580-582`

```java
public static Path defaultWorkspace() {
    return Constants.DEFAULT_WORKSPACE_DIR;
}
```

它是静态方法、返回写死常量，**没有 setter，也没有落盘键**。会话没绑工作区时由 `Main.resolveWorkspace` 回落到它。

**影响**：把 `defaultWorkspace` 列进"运行时配置"并给出 setter，等于凭空新增一次持久化改造；而 §10.3 又声明"本层不负责持久化实现"。

**建议**：要么把 `setDefaultWorkspace` 从 `RuntimeConfig` 移出、标注为待新增的配置项（并补一条决策：默认工作区是否可改、存在哪）；要么删掉这个 setter，只读。

### P0-4 `activeProfile` / `setActiveProfile` 与现有设计方向相反

**位置**：§7.6 `RuntimeConfig`（第 242-243 行）

**代码**：`AppSettings` 类注释（`AppSettings.java:26`）：

> 没有活动方案概念：用哪套配置由输入区选中的模型所属方案决定（跨方案路由见 `Main.streamReply`）。

实际路由走 `Conversation.modelProfile` + `findProfileOwningModel` 反查（`Main.java:329-341`）。这是当初**刻意**删掉的委托 getter，文档又把它当既有配置项加了回来。

**影响**：如果按文档实现 `setActiveProfile`，会与"模型属于哪个方案"的路由规则产生两个真相源；前端切了 activeProfile 但会话消息仍按模型反查，行为不可预期。

**建议**：删掉 `activeProfile` / `setActiveProfile`，改为在会话级 `setModel(sessionId, profileName, modelName)` 上承载——这已经是现有语义。

### P0-5 §4.2 "读取必须保证全量"已经是现状，不是新增改造

**位置**：§4.2（第 61-66 行）、§12 第 2 步

**代码**：`Conversation.getMessages()`（`Conversation.java:196-199`）已经调用 `ensureLoaded()`（`:111-120`），首次触达自动读盘补齐；`isKnownEmpty()` 只对已加载的会话判空。

**影响**：§4.2 被列为"整层成本最高"之外的第二项前置改造，但这里其实没有改造量。真正的风险是**投影实现时绕开 `getMessages()` 直接读 `messages` 字段**，那是个新代码约束，不是存量改造。

**建议**：§4.2 从"前置约束"降为"投影实现的硬约束"一句话：投影禁止直接读 `messages` 字段，必须经 `getMessages()`；§12 第 2 步相应简化，只保留快照原子性。

## 二、P1 内部矛盾（4 条）

### P1-1 `SUPERSEDED` 与"截断重跑"不能并存

**位置**：§8.4（第 311 行）、§8.6（第 319-321 行）、§6 `MessageState`

§8.4 要求六态覆盖"被重跑作废的旧消息"（即 `SUPERSEDED`）；§8.6 又把 `regenerate` 定义成"截断到该点并重跑"。截断后旧消息已不在列表里，`SUPERSEDED` 永远不会出现。

两者只能留一个：

- **截断**（与现有 `removeLastMessage` 一致）：删掉 `SUPERSEDED`，五态即可；
- **标记作废**：`regenerate` 不删消息，但要额外回答"作废消息是否进上下文"——这正是 §8.5 留给决策 4 的问题，会连带受影响。

**建议**：选截断，六态改五态；若坚持保留 `SUPERSEDED`，§8.6 必须改成"标记作废 + 上下文裁剪"，并把它并入决策 4。

### P1-2 §11.2 的判据否定了本层的投影

**位置**：§11.2 第 404 行"遮住参数名只看类型仍能猜出用途：类型选对了；到处是 `String` 则没有"

而 §6、§7 的投影里：

- `SessionView.modelProfile / reasoningEffort / agentMode`：全是 `String`
- `AppCommands.setReasoningEffort(sessionId, effort)` / `setAgentMode(sessionId, mode)`：有效值是 `spi/enums` 里现成的 `ReasoningEffortEnum`（7 值）/ `AgentMode`（4 值），前端拿不到枚举来源就做不出下拉框
- `ToolView.statusDetail`：把工具卡五态压成一个 `String`
- `Request.payload`：整个工具上下文压成一个 `String`

**建议**：二选一时优先改投影——`effort` / `mode` 用枚举（或 `String` + `RuntimeConfig` 里给 `List<String> reasoningEfforts()` / `agentModes()`）；`ToolView` 补 `ToolState` 枚举；`payload` 至少给 `TOOL_APPROVAL` 一个结构化 record。否则就该把 §11.2 这条判据放宽，别让判据和投影互相打脸。

### P1-3 把"必须轮询"列为反例，审批却只有拉取口

**位置**：§5 四种流量表（第 75 行）、§7.5 `HostRequests`（第 229-231 行）、§11.3 第 412 行

§5 把"核心→前端 宿主请求"画成一条流量，但接口只给了 `pending()` 这个查询，事件里没有任何"新审批到来"的推送（`StateEvent` 全集见 §7.4，没有 `HostRequestRaised`）。前端要知道有审批，只能轮询 `pending()`。

**影响**：§11.3 明确把"需轮询才能知道一轮是否结束"列为设计走歪的反例；同一份文档里审批却只能轮询。Swing 侧现在是 `handle.requestApproval(decision)` 主动推，换成投影后反而退化。

**建议**：加 `HostRequestOpened(requestId, sessionId, kind, deadline, seq)` / `HostRequestClosed(requestId, seq)` 两个事件，`pending()` 退回它应有的用途——**补拿**（前端重连/重启），不是**发现**。

### P1-4 事件类型接不上 `subscribe`

**位置**：§7.4（第 186-212 行）、§7.1 `AppEvents.subscribe(long sinceSeq, EventListener listener)`

按现在的写法逐个数：

- 声明 `implements StateEvent` 的 6 个：`SessionRemoved` / `SessionRenamed` / `SessionPinned` / `ActiveSessionChanged` / `RoundStarted` / `RoundCancelled`
- 其中 `SessionCreated(SessionSummary s, long seq)` 组件名是 `s`，**没有 `sessionId()` 访问器**，编译不过
- 带 `sessionId + seq` 却不声明 `implements` 的 10 个：`MessageAppended` / `MessageDelta` / `MessageCompleted` / `ToolStatusChanged` / `UserMessageConfirmed` / `UserMessageRejected` / `RoundFinished` / `RoundFailed` / `ConfigChanged`

另外两处：

- `sealed interface StateEvent` 的实现在同一份文档里是顶层 record，跨文件实现 sealed 接口必须显式 `permits`，否则不合法；
- `EventListener` 全文未定义，`subscribe` 的签名落不了地。

**建议**：明确 `StateEvent` 是否为事件流根类型（是就全部 implements，并把 `permits` 写出来）；`EventListener` 给出 `void onEvent(StateEvent e)` 的定义；`SessionCreated` 改成 `(String sessionId, SessionSummary summary, long seq)`。

## 三、P2 覆盖缺口（12 条）

### P2-1 漏了最硬的前置约束：agent 链与 `Window` 耦合

**位置**：§4 前置约束（只列了消息 id 与全量读取）、§12 第 3 步

`Main` 是纯静态类，`window` 是静态字段，`main()` 里 `new Window("Agent")` 之后所有回调都挂在它上面。链路上与 `Window` 的触点至少 8 类：

| 触点 | 位置 | 作用 |
|---|---|---|
| `getStore()` | `Main:102,153,190,267,539` | 取状态树 |
| `setConversationGenerating` | `:226,250` | 生成态 |
| `addAiMessage` | `:271` | 建 AI 占位卡 |
| `addToolCall` | `:625` | 建工具卡 |
| `addNotifyMessage` | `:198,476,484` | 错误/提示 |
| `onBackGroundTaskDone` | `:521` | 后台结果上屏 |
| `getSelectedEffort` / `getSelectedMode` | `:354,356` | 旧会话回落 |
| `setRealtimeInfo` | `:107` | 停止提示 |

无头运行时 `window == null`，`loop()` 第一步就 NPE；`apiEnsureSession` / `apiInject` 现在也直接抛 `IllegalStateException("应用窗口尚未初始化完成")`。

**影响**：§12 第 3 步"最小面接口 + stdout 假前端"在现状下不可能跑起来——不是接口不够，是链根本发不出去。

**建议**：在 §4 增加 4.3"agent 链必须脱离 UI"，并把它排在落地顺序第 0 位：抽一个输出端口（`setGenerating` / `appendAi` / `appendToolCall` / `notify` / `requestApproval` / `onBackgroundDone` / 取默认 effort+mode），Swing 侧实现该端口，`Main` 只依赖端口。这一步做完，stdout 假前端才有落脚点。

### P2-2 状态树住在 `frontend`，且自带持久化

**位置**：§2 目标 2"前端零持久化"、§10.3

`ConversationStore`（586 行，含 `Files.writeString` / `Path` / `ATOMIC_MOVE`）、`Conversation`、`Message`、`AppSettings`（917 行，含 `Properties` 落盘）全部在 `io.github.preschoolller.agentjava.frontend.store`。

**影响**：现在的"前端"实际是状态+持久化的所有者，"后端"（`Main`）反过来依赖前端。目标架构要求反过来。这不是接口问题，是包与依赖方向的问题，且落地顺序里没有这一步。

**建议**：§12 插入一步"状态树搬家"（`frontend.store` → core 包，与 UI 无关），排在消息 id 之前或并行；并明确搬完后 `frontend` 只剩渲染。

### P2-3 没有通知事件

**位置**：§7.4 事件全集

现有唯一的错误/提示出口是 `window.addNotifyMessage`，3 处调用：启动链失败（`Main:198`）、流式错误（`:476`）、流式异常（`:484`）。投影里没有任何承载物——`RoundFailed` 只覆盖"这一轮失败"，覆盖不了"链还没开始就失败"。

**建议**：补 `Notice(sessionId|null, level, text, seq)`，或明确 `RoundFailed` 兼管启动失败并给出 `sessionId` 可为空的约定。

### P2-4 后台任务整条链不在投影里

**位置**：§7.4、§6 `ToolView`

`whenBackgroundTaskDone`（`Main:516-527`）会在**空闲会话上自行起一条新链**，不需要任何 `submit`；`PENDING_BG_DELIVERY` 负责"结果落在快照之后"的补偿续轮。工具卡还有 `bg-running` / `bg-done` / `bg-killed` 三个状态（`Conversation.java:24-28`），以及崩溃恢复时由 `running` 翻成的 `interrupted`（`ConversationStore.java:539-545`）。

**影响**：
- `RoundStarted` 可能在没有 `submit` 的情况下出现，前端若按"submit 后才有轮次"建模会错；
- `ToolView.statusDetail` 一个 `String` 吞掉五态 + 后台三态，前端无法判断"这轮结束了但工具还在跑"，也无法挂"终止后台任务"的入口。

**建议**：`ToolView` 补 `ToolState` 枚举（`RUNNING / WAITING_APPROVAL / OK / ERROR / INTERRUPTED / BG_RUNNING / BG_DONE / BG_KILLED`）；补 `BackgroundTaskFinished(sessionId, messageId, callId, seq)`；并在 §6 说明 `RoundStarted` 的两种来源（用户提交 / 后台结果驱动）。

### P2-5 `Request` 缺 `callId`

**位置**：§7.5 `Request(requestId, sessionId, kind, payload, deadlineEpochMs)`

现有审批是挂在具体工具卡上的：`callIdHandleMap.get(toolCall.getCallId())`（`Main:561`），卡片缺失就直接拒绝。前端拿到 `Request` 后无法知道该把"允许/拒绝"挂到哪张卡片，除非去解析 `payload` 这个不透明字符串。

**建议**：`Request` 补 `String callId`（可为空，对应 `USER_INPUT` / `CONFIRM`）；或把 `payload` 按 `Kind` 拆成三个结构化 record。

### P2-6 `submit` 的并发语义未定义

**位置**：§7.3（"全部异步、立即返回"）、§8.3（`UserMessageRejected`）

现有实现：抢不到会话锁直接静默 return（`Main:186-188`）；外部注入路径先记 `PENDING_BG_DELIVERY` 再抢锁（`:178`），由链首快照消化。

文档只说"异步立即返回"，没说会话忙时怎么办；`UserMessageRejected` 有签名却没有触发条件。三种可能（排队 / 并入当轮 / 拒绝）对前端影响完全不同：拒绝要回滚乐观更新，排队要显示第 N 位，并入则不需要额外 UI。

**建议**：新增一条决策（见 §六 决策 11），并在 §7.3 写明默认值；`UserMessageRejected` 明确只在"会话不存在 / 参数非法 / 显式拒绝策略"时发出。

### P2-7 `createSession` / `selectSession` 有隐藏副作用

**位置**：§7.3

- `newConversation`（`ConversationStore:83-101`）：当前会话若是空会话，**直接复用并改它的 workspace**，返回的不是新 id；
- `switchTo`（`:131-135`）：离开当前空会话时**删除该会话及其落盘文件**。

两者都是刻意的产品行为（避免堆空会话），但契约里一个字都没写。JS 前端按"create 必得新 id"或"select 不改数据"建模，会直接踩。

**建议**：在 §7.3 两条方法下各加一句副作用说明；或把"复用空会话""清理空会话"上升为显式参数/返回值（例如 `createSession` 返回 `SessionSummary` 并带 `reused` 标记）。

### P2-8 长会话全量传输

**位置**：§6 `SessionView.messages`、§8.1"快照与 seq 原子"

现有 UI 对长会话做了视口窗口化（README 功能列表），但投影要求 `session(id)` 一次返回全部消息，且 §8.1 禁止"部分快照"。含 bash 输出的会话单条结果可达数十 KB，几百条消息走 HTTP 会把首屏拖死。

**建议**：新增一条决策（见 §六 决策 13），二选一：`messages` 只给尾部窗口 + `hasMoreBefore / beforeCursor`；或保留全量但给单条 `ToolView.result` 加截断上限与按需拉取接口。

### P2-9 配置面不足以驱动设置面板

**位置**：§7.6 `RuntimeConfig`

现有 `SettingsDialog` 依赖而投影没有的能力：

| 能力 | 现状 |
|---|---|
| 方案增 / 删 / 改名 / 整体提交 | `addProfile` / `removeProfile` / `renameProfile` / `applyProfiles` |
| 方案内字段编辑 | `Profile.setBackendUrl/Key/Model/Temperature/MaxTokens/SystemPrompt/ModelMetas` |
| MCP 名单写入 | `setMcpServers(List<McpServer>)` |
| provider 选择 | `setActiveProviderName(apiType, name)` |
| 上下文处理器选择 | `setActiveContextHandler(name)` |

`RuntimeConfig` 只给了 `profiles()` 列表 + `setActiveProfile`（见 P0-4，还要删）。按现在这份接口，JS 前端做不出设置页。

**建议**：补 `upsertProfile(String name, ProfileInput)` / `deleteProfile(String)` / `renameProfile(String, String)` / `setMcpServers(List<McpServerView>)` / `setActiveProvider(String apiType, String provider)` / `setActiveContextHandler(String)`；或者明确"配置面首版只读，编辑仍归 Swing"，并把它写进非目标。

### P2-10 `enabledTools` 三态丢失、`toolProperty` 与插件命名空间同池

**位置**：§7.6 `enabledTools()` / `setEnabledTools(List<String>)` / `toolProperty(toolId, key)`

- `AppSettings.getEnabledTools()`（`:472-477`）有**三态**：`null` = 从未配置（全部启用，含未来新工具）/ `空列表` = 显式全不启用 / 列表 = 部分。压成一个 `List<String>` 后，`null` 与空列表的区别没了，前端无法表达"恢复默认"。
- `AppSettings.toolProperties`（`:110`）里实际只有 `plugin-properties.<插件名>` 这一种键（`load()` 只回填该前缀，`:815-819`），且 `getPersistentPluginInput` 读的是 `properties` 快照、`setPersistentPluginInput` 写的是 `toolProperties`。文档的 `toolProperty(toolId, key)` 会与插件持久化输入共用一张表，不写命名空间必然撞键。

**建议**：`enabledTools` 的返回值与入参都标注 `@Nullable`，并写明 null 语义；`toolProperty` 的 key 定义为 `tool.<toolId>.<key>`，与 `plugin-properties.*` 显式隔离，并在契约里禁止前端读写 `plugin-` 前缀。

### P2-11 `subscribe` 的重放与缺口

**位置**：§7.1 `subscribe(long sinceSeq, EventListener listener)`、§8.1

§8.1 的整个论证建立在"订阅能从某个 seq 续上"之上，但全文没说：

- 是否重放 `sinceSeq` 之后的历史事件（重放则需缓存上限，不重放则 `sinceSeq` 无意义）；
- 缓存窗口多大、超出后怎么报（`EventGap`？强制重新拉快照？）；
- 慢消费者会不会被丢弃。

**建议**：新增一条决策（见 §六 决策 12），至少写明"环形缓冲 N 条，超出返回 `GapDetected`，前端重新拉 `snapshot()` + `session()`"。

### P2-12 消息 id 与 fork

**位置**：§4.1

`Conversation.fork` 用 `message.copy()` 复制前缀（`Conversation.java:253-261`），`copy()` 原样复制全部 8 个字段（`Message.java:40-42`）。加了 id 之后，分叉会话会复制出一批**与源会话完全相同的 messageId**。

**影响**：如果前端把 messageId 当全局 key（React key、TUI 行缓存），跨会话切分叉会串行；如果只当会话内 key 就没问题——但这条契约没人写。

**建议**：§4.1 明确二选一：id 只保证会话内唯一（并说明跨会话重复是合法的）；或 `copy()` 重新发号（成本是多一次 UUID，但前端 key 可以直接用）。倾向前者，后者会让"分叉前后同一条消息"失去关联。

## 四、P3 细节（6 条）

1. **`Role` 类型全文未定义**（§6 `MessageView.role` 引用它）。`spi/enums/RoleEnum` 已有 `USER / ASSISTANT / TOOL_RESULT / CONTEXT_MARKER`，投影另立一套 `Role` 会漂移。建议直接复用或写明映射（尤其 `CONTEXT_MARKER`：现有消息列表里有压缩水位线标记，`MessageView` 若不过滤，前端会渲染出一条空消息）。
2. **`ConfigChanged(key, sessionId, …)` 对全局配置没有 `sessionId` 可用**（`profiles` / `mcpServers` / `enabledTools` 都是全局）。建议 `sessionId` 允许 null 并写明含义，或拆 `SessionConfigChanged` / `GlobalConfigChanged`。
3. **`MessageCompleted` 不带最终文本**。前端漏了 delta（重连、被截断）就只能重新拉 `session()`。建议在 §7.4 写明"`MessageCompleted` 只是收束信号，正文以 delta 累积为准，缺失时重拉 `session()`"。
4. **新层放哪个包没说**，而 `io.github.preschoolller.agentjava.api` 已被插件会话门面 `AgentJavaSessions` 占用。两个"api"会在阅读和 import 上打架，建议先定名（如 `core.app` / `application`）。
5. **没提回归测试**。项目惯例是改完跑 `mvn test` + `WindowGuiTest`（见 `foragent/组件计划.md` 首段）；§11.1 的假前端天然适合接进回归（3 轮 + 1 次取消 + 1 次审批），建议写成可执行断言而不是"能跑就算够用"。
6. **"AI 不得代工"这条写在文档正文第 14 行**，位置偏弱——后续 agent 不打开这个文件就看不到。建议同时落到 README 或仓库级 agent 指令里，否则约束只在"读到的人"身上生效。
