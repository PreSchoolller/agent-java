# 应用抽象层设计 · 评审意见

> 评审对象：《应用抽象层设计》v0.1（`c5acfa2`）、v0.2（`01af5ad`）、v0.3（`ffdfab1`）
> 评审依据：当前 `app` / `spi` 源码（branch `api_use_app`）
> 评审范围：只评审设计与契约本身。未改动 `app/`、`spi/` 任何源码，也未修改原文档。
> 结论：**骨架成立，可以按此方向走**；v0.1 有 5 处与代码事实不符、4 处自相矛盾、12 处覆盖缺口，按现状实现会在第二个前端出现时集中返工。
> **第二轮复审（v0.2）见 §七：上轮 27 条已落地 22 条，新增 7 条（含 2 条 P0），建议 v0.3 先处理这 7 条再进入实现。**
> **第三轮复审（v0.3）见 §八：上一轮 13 条落地 8 条，两条 P0 未闭合（工具句柄仍缺、`activeId` 归属修反），建议 v0.4 只收这两条加一处退役时机。**

## 总览

| 级别 | 含义 | 条数 |
|---|---|---|
| P0 | 与现有代码事实不符，照做会走错方向 | 5 |
| P1 | 文档内部两处不能同时成立 | 4 |
| P2 | 契约覆盖缺口，实现后才发现补不动 | 12 |
| P3 | 细节与表述 | 6 |

三句话总结：

1. **最硬的前置约束漏了。** 不是消息 id，是 agent 链与 `Window` 的耦合——`Main` 里 23 处 `window.`、24 处 `SwingUtilities.`，`main()` 第一件事就是 `new Window(...)`。不改这条，§12 第 3 步的 stdout 假前端根本启动不了。
2. **目标与包结构对立。** 状态树（`ConversationStore` / `Conversation` / `Message` / `AppSettings`）现在全在 `frontend.store`，且持久化就在同一个类里。"前端零持久化"要求先把这四个类搬到 core，落地顺序里没有这一步。
3. **两条非常规流量各有半截没接上。** 审批只有 `pending()` 拉取口、没有"新请求到来"的推送；后台任务能在空闲会话上自行起新链，投影里却没有任何对应事件。

## 一、P0 与代码事实不符（5 条）

### P0-1 无头模式下审批不会"永久挂死"，而是自动拒绝

**位置**：§8.7（第 323-327 行）、决策 5

**代码**：`Main.requestToolApproval`（`Main.java:551-597`）

```java
Window.ToolCallHandle handle = callIdHandleMap.get(toolCall.getCallId());
if (handle == null || cancelled.get()) {
    LOG.info("审批自动拒绝：handle={} cancelled={}", ...);
    return false;
}
```

`ToolApprovalGate` 确实无超时、在工具执行线程上同步阻塞，但阻塞的实现是每 200ms 醒一次看 `cancelled`（`decision.get(200, MILLISECONDS)`），**没有卡片就立刻返回 false**。无头模式不创建 `ToolCallHandle`，所以行为是"静默拒绝所有需审批的工具"，不是"挂死"。

**影响**：决策 5 的三个选项（自动拒绝 / 自动放行 / 挂起等超时）缺了"保持现状"这个基线。而"静默拒绝"比"挂死"更难排查——无头跑一轮会得到一堆工具不执行的对话，没有任何错误信号。

**建议**：§8.7 改写为三种既有行为并列：有卡片等点击 / 无卡片即拒绝 / 用户停止即拒绝；决策 5 增加"保持自动拒绝"基线，并要求 `HostRequests` 显式声明无头时的默认动作与可审计的拒绝事件。

### P0-2 §4.1 的改造清单：数量与对象都不准

**位置**：§4.1 第 55 行"`ConversationStore` 中 6 个按引用更新的方法改为按 `messageId`"

**代码**：`ConversationStore.java` 里更新已存在消息的方法确实是 6 个，但定位方式分两类：

| 方法 | 定位方式 | 是否该改 `messageId` |
|---|---|---|
| `updateMessageText(id, target, text)` | 对象引用 | 是 |
| `updateMessageContent(id, target, text, thinking)` | 对象引用 | 是 |
| `completeToolCall(id, target, result, success, arguments)` | 对象引用 | 是 |
| `fork(id, target)` | 对象引用 | 是（入参改成 `fromMessageId`） |
| `completeBackGroundTask(id, callId, output)` | `callId` | **否**——后台回调线程只有 `callId` |
| `terminateBackGroundTask(id, callId)` | `callId` | **否**——同上 |

即"4 个按引用 + 2 个按 callId"，不是"6 个按引用"。另外文档只列了 3 个签名，**漏了 `fork`**——而 §7.3 的 `forkSession(sessionId, fromMessageId)` 恰恰要求它改。

**建议**：清单按两类重写，明确"按 `callId` 的两个保持不动"；补 `fork` 与 `Conversation` 内部的 5 个同名方法（`updateMessageText` / `updateToolResult` / `updateMessageContent` / `updateBackGroundResult` / `updateBackGroundKilled`）。

### P0-3 `defaultWorkspace` 不是配置字段，`setDefaultWorkspace` 不存在

**位置**：§7.6 `RuntimeConfig`（第 246 行）、§7.6 三分表第 259 行

**代码**：`AppSettings.java:580-582`

```java
public static Path defaultWorkspace() {
    return Constants.DEFAULT_WORKSPACE_DIR;
}
```

它是静态方法、返回写死常量，**没有 setter，也没有落盘键**。会话没绑工作区时由 `Main.resolveWorkspace` 回落到它。

**影响**：把 `defaultWorkspace` 列进"运行时配置"并给出 setter，等于凭空新增一次持久化改造；而 §10.3 又声明"本层不负责持久化实现"。

**建议**：要么把 `setDefaultWorkspace` 从 `RuntimeConfig` 移出、标注为待新增的配置项（并补一条决策：默认工作区是否可改、存在哪）；要么删掉这个 setter，只读。

### P0-4 `activeProfile` / `setActiveProfile` 与现有设计方向相反

**位置**：§7.6 `RuntimeConfig`（第 242-243 行）

**代码**：`AppSettings` 类注释（`AppSettings.java:26`）：

> 没有活动方案概念：用哪套配置由输入区选中的模型所属方案决定（跨方案路由见 `Main.streamReply`）。

实际路由走 `Conversation.modelProfile` + `findProfileOwningModel` 反查（`Main.java:329-341`）。这是当初**刻意**删掉的委托 getter，文档又把它当既有配置项加了回来。

**影响**：如果按文档实现 `setActiveProfile`，会与"模型属于哪个方案"的路由规则产生两个真相源；前端切了 activeProfile 但会话消息仍按模型反查，行为不可预期。

**建议**：删掉 `activeProfile` / `setActiveProfile`，改为在会话级 `setModel(sessionId, profileName, modelName)` 上承载——这已经是现有语义。

### P0-5 §4.2 "读取必须保证全量"已经是现状，不是新增改造

**位置**：§4.2（第 61-66 行）、§12 第 2 步

**代码**：`Conversation.getMessages()`（`Conversation.java:196-199`）已经调用 `ensureLoaded()`（`:111-120`），首次触达自动读盘补齐；`isKnownEmpty()` 只对已加载的会话判空。

**影响**：§4.2 被列为"整层成本最高"之外的第二项前置改造，但这里其实没有改造量。真正的风险是**投影实现时绕开 `getMessages()` 直接读 `messages` 字段**，那是个新代码约束，不是存量改造。

**建议**：§4.2 从"前置约束"降为"投影实现的硬约束"一句话：投影禁止直接读 `messages` 字段，必须经 `getMessages()`；§12 第 2 步相应简化，只保留快照原子性。

## 二、P1 内部矛盾（4 条）

### P1-1 `SUPERSEDED` 与"截断重跑"不能并存

**位置**：§8.4（第 311 行）、§8.6（第 319-321 行）、§6 `MessageState`

§8.4 要求六态覆盖"被重跑作废的旧消息"（即 `SUPERSEDED`）；§8.6 又把 `regenerate` 定义成"截断到该点并重跑"。截断后旧消息已不在列表里，`SUPERSEDED` 永远不会出现。

两者只能留一个：

- **截断**（与现有 `removeLastMessage` 一致）：删掉 `SUPERSEDED`，五态即可；
- **标记作废**：`regenerate` 不删消息，但要额外回答"作废消息是否进上下文"——这正是 §8.5 留给决策 4 的问题，会连带受影响。

**建议**：选截断，六态改五态；若坚持保留 `SUPERSEDED`，§8.6 必须改成"标记作废 + 上下文裁剪"，并把它并入决策 4。

### P1-2 §11.2 的判据否定了本层的投影

**位置**：§11.2 第 404 行"遮住参数名只看类型仍能猜出用途：类型选对了；到处是 `String` 则没有"

而 §6、§7 的投影里：

- `SessionView.modelProfile / reasoningEffort / agentMode`：全是 `String`
- `AppCommands.setReasoningEffort(sessionId, effort)` / `setAgentMode(sessionId, mode)`：有效值是 `spi/enums` 里现成的 `ReasoningEffortEnum`（7 值）/ `AgentMode`（4 值），前端拿不到枚举来源就做不出下拉框
- `ToolView.statusDetail`：把工具卡五态压成一个 `String`
- `Request.payload`：整个工具上下文压成一个 `String`

**建议**：二选一时优先改投影——`effort` / `mode` 用枚举（或 `String` + `RuntimeConfig` 里给 `List<String> reasoningEfforts()` / `agentModes()`）；`ToolView` 补 `ToolState` 枚举；`payload` 至少给 `TOOL_APPROVAL` 一个结构化 record。否则就该把 §11.2 这条判据放宽，别让判据和投影互相打脸。

### P1-3 把"必须轮询"列为反例，审批却只有拉取口

**位置**：§5 四种流量表（第 75 行）、§7.5 `HostRequests`（第 229-231 行）、§11.3 第 412 行

§5 把"核心→前端 宿主请求"画成一条流量，但接口只给了 `pending()` 这个查询，事件里没有任何"新审批到来"的推送（`StateEvent` 全集见 §7.4，没有 `HostRequestRaised`）。前端要知道有审批，只能轮询 `pending()`。

**影响**：§11.3 明确把"需轮询才能知道一轮是否结束"列为设计走歪的反例；同一份文档里审批却只能轮询。Swing 侧现在是 `handle.requestApproval(decision)` 主动推，换成投影后反而退化。

**建议**：加 `HostRequestOpened(requestId, sessionId, kind, deadline, seq)` / `HostRequestClosed(requestId, seq)` 两个事件，`pending()` 退回它应有的用途——**补拿**（前端重连/重启），不是**发现**。

### P1-4 事件类型接不上 `subscribe`

**位置**：§7.4（第 186-212 行）、§7.1 `AppEvents.subscribe(long sinceSeq, EventListener listener)`

按现在的写法逐个数：

- 声明 `implements StateEvent` 的 6 个：`SessionRemoved` / `SessionRenamed` / `SessionPinned` / `ActiveSessionChanged` / `RoundStarted` / `RoundCancelled`
- 其中 `SessionCreated(SessionSummary s, long seq)` 组件名是 `s`，**没有 `sessionId()` 访问器**，编译不过
- 带 `sessionId + seq` 却不声明 `implements` 的 10 个：`MessageAppended` / `MessageDelta` / `MessageCompleted` / `ToolStatusChanged` / `UserMessageConfirmed` / `UserMessageRejected` / `RoundFinished` / `RoundFailed` / `ConfigChanged`

另外两处：

- `sealed interface StateEvent` 的实现在同一份文档里是顶层 record，跨文件实现 sealed 接口必须显式 `permits`，否则不合法；
- `EventListener` 全文未定义，`subscribe` 的签名落不了地。

**建议**：明确 `StateEvent` 是否为事件流根类型（是就全部 implements，并把 `permits` 写出来）；`EventListener` 给出 `void onEvent(StateEvent e)` 的定义；`SessionCreated` 改成 `(String sessionId, SessionSummary summary, long seq)`。

## 三、P2 覆盖缺口（12 条）

### P2-1 漏了最硬的前置约束：agent 链与 `Window` 耦合

**位置**：§4 前置约束（只列了消息 id 与全量读取）、§12 第 3 步

`Main` 是纯静态类，`window` 是静态字段，`main()` 里 `new Window("Agent")` 之后所有回调都挂在它上面。链路上与 `Window` 的触点至少 8 类：

| 触点 | 位置 | 作用 |
|---|---|---|
| `getStore()` | `Main:102,153,190,267,539` | 取状态树 |
| `setConversationGenerating` | `:226,250` | 生成态 |
| `addAiMessage` | `:271` | 建 AI 占位卡 |
| `addToolCall` | `:625` | 建工具卡 |
| `addNotifyMessage` | `:198,476,484` | 错误/提示 |
| `onBackGroundTaskDone` | `:521` | 后台结果上屏 |
| `getSelectedEffort` / `getSelectedMode` | `:354,356` | 旧会话回落 |
| `setRealtimeInfo` | `:107` | 停止提示 |

无头运行时 `window == null`，`loop()` 第一步就 NPE；`apiEnsureSession` / `apiInject` 现在也直接抛 `IllegalStateException("应用窗口尚未初始化完成")`。

**影响**：§12 第 3 步"最小面接口 + stdout 假前端"在现状下不可能跑起来——不是接口不够，是链根本发不出去。

**建议**：在 §4 增加 4.3"agent 链必须脱离 UI"，并把它排在落地顺序第 0 位：抽一个输出端口（`setGenerating` / `appendAi` / `appendToolCall` / `notify` / `requestApproval` / `onBackgroundDone` / 取默认 effort+mode），Swing 侧实现该端口，`Main` 只依赖端口。这一步做完，stdout 假前端才有落脚点。

### P2-2 状态树住在 `frontend`，且自带持久化

**位置**：§2 目标 2"前端零持久化"、§10.3

`ConversationStore`（586 行，含 `Files.writeString` / `Path` / `ATOMIC_MOVE`）、`Conversation`、`Message`、`AppSettings`（917 行，含 `Properties` 落盘）全部在 `io.github.preschoolller.agentjava.frontend.store`。

**影响**：现在的"前端"实际是状态+持久化的所有者，"后端"（`Main`）反过来依赖前端。目标架构要求反过来。这不是接口问题，是包与依赖方向的问题，且落地顺序里没有这一步。

**建议**：§12 插入一步"状态树搬家"（`frontend.store` → core 包，与 UI 无关），排在消息 id 之前或并行；并明确搬完后 `frontend` 只剩渲染。

### P2-3 没有通知事件

**位置**：§7.4 事件全集

现有唯一的错误/提示出口是 `window.addNotifyMessage`，3 处调用：启动链失败（`Main:198`）、流式错误（`:476`）、流式异常（`:484`）。投影里没有任何承载物——`RoundFailed` 只覆盖"这一轮失败"，覆盖不了"链还没开始就失败"。

**建议**：补 `Notice(sessionId|null, level, text, seq)`，或明确 `RoundFailed` 兼管启动失败并给出 `sessionId` 可为空的约定。

### P2-4 后台任务整条链不在投影里

**位置**：§7.4、§6 `ToolView`

`whenBackgroundTaskDone`（`Main:516-527`）会在**空闲会话上自行起一条新链**，不需要任何 `submit`；`PENDING_BG_DELIVERY` 负责"结果落在快照之后"的补偿续轮。工具卡还有 `bg-running` / `bg-done` / `bg-killed` 三个状态（`Conversation.java:24-28`），以及崩溃恢复时由 `running` 翻成的 `interrupted`（`ConversationStore.java:539-545`）。

**影响**：
- `RoundStarted` 可能在没有 `submit` 的情况下出现，前端若按"submit 后才有轮次"建模会错；
- `ToolView.statusDetail` 一个 `String` 吞掉五态 + 后台三态，前端无法判断"这轮结束了但工具还在跑"，也无法挂"终止后台任务"的入口。

**建议**：`ToolView` 补 `ToolState` 枚举（`RUNNING / WAITING_APPROVAL / OK / ERROR / INTERRUPTED / BG_RUNNING / BG_DONE / BG_KILLED`）；补 `BackgroundTaskFinished(sessionId, messageId, callId, seq)`；并在 §6 说明 `RoundStarted` 的两种来源（用户提交 / 后台结果驱动）。

### P2-5 `Request` 缺 `callId`

**位置**：§7.5 `Request(requestId, sessionId, kind, payload, deadlineEpochMs)`

现有审批是挂在具体工具卡上的：`callIdHandleMap.get(toolCall.getCallId())`（`Main:561`），卡片缺失就直接拒绝。前端拿到 `Request` 后无法知道该把"允许/拒绝"挂到哪张卡片，除非去解析 `payload` 这个不透明字符串。

**建议**：`Request` 补 `String callId`（可为空，对应 `USER_INPUT` / `CONFIRM`）；或把 `payload` 按 `Kind` 拆成三个结构化 record。

### P2-6 `submit` 的并发语义未定义

**位置**：§7.3（"全部异步、立即返回"）、§8.3（`UserMessageRejected`）

现有实现：抢不到会话锁直接静默 return（`Main:186-188`）；外部注入路径先记 `PENDING_BG_DELIVERY` 再抢锁（`:178`），由链首快照消化。

文档只说"异步立即返回"，没说会话忙时怎么办；`UserMessageRejected` 有签名却没有触发条件。三种可能（排队 / 并入当轮 / 拒绝）对前端影响完全不同：拒绝要回滚乐观更新，排队要显示第 N 位，并入则不需要额外 UI。

**建议**：新增一条决策（见 §六 决策 11），并在 §7.3 写明默认值；`UserMessageRejected` 明确只在"会话不存在 / 参数非法 / 显式拒绝策略"时发出。

### P2-7 `createSession` / `selectSession` 有隐藏副作用

**位置**：§7.3

- `newConversation`（`ConversationStore:83-101`）：当前会话若是空会话，**直接复用并改它的 workspace**，返回的不是新 id；
- `switchTo`（`:131-135`）：离开当前空会话时**删除该会话及其落盘文件**。

两者都是刻意的产品行为（避免堆空会话），但契约里一个字都没写。JS 前端按"create 必得新 id"或"select 不改数据"建模，会直接踩。

**建议**：在 §7.3 两条方法下各加一句副作用说明；或把"复用空会话""清理空会话"上升为显式参数/返回值（例如 `createSession` 返回 `SessionSummary` 并带 `reused` 标记）。

### P2-8 长会话全量传输

**位置**：§6 `SessionView.messages`、§8.1"快照与 seq 原子"

现有 UI 对长会话做了视口窗口化（README 功能列表），但投影要求 `session(id)` 一次返回全部消息，且 §8.1 禁止"部分快照"。含 bash 输出的会话单条结果可达数十 KB，几百条消息走 HTTP 会把首屏拖死。

**建议**：新增一条决策（见 §六 决策 13），二选一：`messages` 只给尾部窗口 + `hasMoreBefore / beforeCursor`；或保留全量但给单条 `ToolView.result` 加截断上限与按需拉取接口。

### P2-9 配置面不足以驱动设置面板

**位置**：§7.6 `RuntimeConfig`

现有 `SettingsDialog` 依赖而投影没有的能力：

| 能力 | 现状 |
|---|---|
| 方案增 / 删 / 改名 / 整体提交 | `addProfile` / `removeProfile` / `renameProfile` / `applyProfiles` |
| 方案内字段编辑 | `Profile.setBackendUrl/Key/Model/Temperature/MaxTokens/SystemPrompt/ModelMetas` |
| MCP 名单写入 | `setMcpServers(List<McpServer>)` |
| provider 选择 | `setActiveProviderName(apiType, name)` |
| 上下文处理器选择 | `setActiveContextHandler(name)` |

`RuntimeConfig` 只给了 `profiles()` 列表 + `setActiveProfile`（见 P0-4，还要删）。按现在这份接口，JS 前端做不出设置页。

**建议**：补 `upsertProfile(String name, ProfileInput)` / `deleteProfile(String)` / `renameProfile(String, String)` / `setMcpServers(List<McpServerView>)` / `setActiveProvider(String apiType, String provider)` / `setActiveContextHandler(String)`；或者明确"配置面首版只读，编辑仍归 Swing"，并把它写进非目标。

### P2-10 `enabledTools` 三态丢失、`toolProperty` 与插件命名空间同池

**位置**：§7.6 `enabledTools()` / `setEnabledTools(List<String>)` / `toolProperty(toolId, key)`

- `AppSettings.getEnabledTools()`（`:472-477`）有**三态**：`null` = 从未配置（全部启用，含未来新工具）/ `空列表` = 显式全不启用 / 列表 = 部分。压成一个 `List<String>` 后，`null` 与空列表的区别没了，前端无法表达"恢复默认"。
- `AppSettings.toolProperties`（`:110`）里实际只有 `plugin-properties.<插件名>` 这一种键（`load()` 只回填该前缀，`:815-819`），且 `getPersistentPluginInput` 读的是 `properties` 快照、`setPersistentPluginInput` 写的是 `toolProperties`。文档的 `toolProperty(toolId, key)` 会与插件持久化输入共用一张表，不写命名空间必然撞键。

**建议**：`enabledTools` 的返回值与入参都标注 `@Nullable`，并写明 null 语义；`toolProperty` 的 key 定义为 `tool.<toolId>.<key>`，与 `plugin-properties.*` 显式隔离，并在契约里禁止前端读写 `plugin-` 前缀。

### P2-11 `subscribe` 的重放与缺口

**位置**：§7.1 `subscribe(long sinceSeq, EventListener listener)`、§8.1

§8.1 的整个论证建立在"订阅能从某个 seq 续上"之上，但全文没说：

- 是否重放 `sinceSeq` 之后的历史事件（重放则需缓存上限，不重放则 `sinceSeq` 无意义）；
- 缓存窗口多大、超出后怎么报（`EventGap`？强制重新拉快照？）；
- 慢消费者会不会被丢弃。

**建议**：新增一条决策（见 §六 决策 12），至少写明"环形缓冲 N 条，超出返回 `GapDetected`，前端重新拉 `snapshot()` + `session()`"。

### P2-12 消息 id 与 fork

**位置**：§4.1

`Conversation.fork` 用 `message.copy()` 复制前缀（`Conversation.java:253-261`），`copy()` 原样复制全部 8 个字段（`Message.java:40-42`）。加了 id 之后，分叉会话会复制出一批**与源会话完全相同的 messageId**。

**影响**：如果前端把 messageId 当全局 key（React key、TUI 行缓存），跨会话切分叉会串行；如果只当会话内 key 就没问题——但这条契约没人写。

**建议**：§4.1 明确二选一：id 只保证会话内唯一（并说明跨会话重复是合法的）；或 `copy()` 重新发号（成本是多一次 UUID，但前端 key 可以直接用）。倾向前者，后者会让"分叉前后同一条消息"失去关联。

### 7.2 新发现（v0.2 引入，7 条）

#### N1 [P0] `AgentSink` 的八个方法驱动不了一轮流式

**位置**：§4.1（第 58-69 行）

端口现在是这样：

```java
void setGenerating(String sessionId, boolean generating);
void appendAi(String sessionId);
void appendToolCall(String sessionId, String toolName, String argsSummary, String callId);
void notify(String sessionId, NoticeLevel level, String text);
Boolean requestApproval(String callId, ApprovalPayload payload);
void onBackgroundDone(String sessionId, String callId, String output);
String defaultEffort(String sessionId);
String defaultMode(String sessionId);
```

对照 `Main` 实际需要的能力，六处不够用：

| 缺口 | 代码依据 | 后果 |
|---|---|---|
| `appendAi` 返回 `void`，没有增量与收尾口 | `Main:427-431` 调 `appendChunk`、`:487` 调 `finish`、`:599-620` 调 `appendThinking`/`finishThinking` | 接上端口后流式正文无处可去，第 0 步直接断流 |
| `appendToolCall` 不带 `messageId` | `Main:625` → `window.addToolCall(...)`；卡片靠 `messageId` 与后续 `ToolStateChanged` 对应 | UI 建了卡却认不出是哪条消息 |
| `appendAi` 不带 `messageId` | 同上，`Main:271` 之后所有更新按消息定位 | 同上 |
| `requestApproval` 缺 `sessionId` | `Main:551-553` 需要 `conversation` 上下文；多会话同开时无法路由 | 审批弹到错的会话 |
| 丢了 `additionalRequest` | `ToolApprovalGate.allow(ToolCall, boolean additionalRequest)`；`Main:554-559` 对"读工作区外"走额外确认 | 额外审批语义消失，`FULL_ACCESS` 下的追问策略失效 |
| `onBackgroundDone` 返回 `void` | `Main:521` 用 `window.onBackGroundTaskDone(...)` 的布尔值决定是否续链 | 后台结果回来后续不续轮变成瞎猜 |

**建议**（签名示意，八条上限仍可守住）：

```java
interface AgentSink {
    void setGenerating(String sessionId, boolean generating);
    AiWriter appendAi(String sessionId, String messageId);           // 句柄带 chunk/thinking/finish
    void appendToolCall(String sessionId, String messageId, String toolName,
                        String argsSummary, String callId);
    void notify(String sessionId, NoticeLevel level, String text);
    Boolean requestApproval(String sessionId, String messageId, String callId,
                            ApprovalPayload payload, boolean additionalRequest);
    boolean onBackgroundDone(String sessionId, String callId, String output);
    String defaultEffort(String sessionId);
    String defaultMode(String sessionId);
}

interface AiWriter {
    void chunk(String text);
    void thinking(String text);
    void finishThinking();
    void finish();
}
```

这也说明 4.3 的消息 id 必须排在 4.1 之前或同批落地——**端口要靠 `messageId` 寻址**，原文把 4.1 排在 id 改造之前（落地顺序 0 → 2），顺序上要调整。

#### N2 [P0] 工具结果的全文没有推送路径

**位置**：§6 `ToolView`、§7.4 `ToolStateChanged`、8.3

工具消息的结果正文确实存在 `MessageView.text` 里（`Message.java:5`，工具消息的 `text` 存结果），所以投影字段本身不缺。缺的是**推送路径**：`ToolStateChanged` 只带 `resultSummary`，`MessageCompleted` 按 7.4 第 2 条明确"不带最终正文"。于是一个 bash 任务完成后，前端手里只有一段摘要，要看全文只能重拉 `session(id)`。

这与 11.3「前端为显示正确需额外调用超过 2 个查询接口」冲突，且长会话重拉代价高（还叠加十三里未定的分页）。现有 Swing 的工具卡是"展开看完整输出、超长内部滚动"（README 功能列表），换成 JS 后这个核心功能没有数据来源。

**建议**：`ToolStateChanged` 增加 `resultText`（完整或按规则截断），或让 `MessageCompleted` 对工具消息携带终态文本；大结果再按决策 7 / 13 的截断与按需拉取规则处理。8.10 现在只讨论了参数（`args`），建议补一句结果的表达。

#### N3 [P1] `Role` 复用 `spi.RoleEnum` 与"前端不该 import spi"直接矛盾

**位置**：§6 第 169 行与第 171 行

- 169 行：`ReasoningEffort` / `AgentMode` 是本层自己的枚举……**前端不该 import `spi`**
- 171 行：`Role` **复用 `spi.enums.RoleEnum`**……不另立一套，避免两边漂移

若 `MessageView.role` 的类型就是 `spi.enums.RoleEnum`，每个前端都必须 import `spi`，169 行立刻失效；若前端只认一个本层枚举，那 171 行就不是"复用"而是"映射"，与 169 行的做法一致。二者取一，别混着写。

**建议**：按 169 行的原则，本层定义 `enum Role { USER, ASSISTANT, TOOL_RESULT }`（`CONTEXT_MARKER` 反正要过滤，不必进枚举），映射写在投影实现里；这样"前端不 import spi"这条规则才守得住。

#### N4 [P1] `GapDetected` 既不在 `permits`，也没进待补清单

**位置**：8.2 第 403 行 vs 7.4 的 `permits` 列表

8.2 要求"`sinceSeq` 早于缓冲起点时，立即回一条 `GapDetected`"，但 7.4 的 `sealed interface StateEvent permits ...` 列了 18 个类型，没有 `GapDetected`；十三的待补清单也没有它（`Notice` 倒是老老实实挂账了）。

按现在的写法，`GapDetected` 要么不是事件（那它怎么"回"给前端？），要么是事件但接不上 `subscribe` 的监听签名。

**建议**：把 `GapDetected(long sinceSeq, long earliestSeq, long seq)` 加进 `permits`，并在 8.2 说明它是"事件流内的控制信号"而非状态变更。

#### N5 [P1] `AgentSink` 与事件流是两条输出路径，端口何时退役没说

**位置**：§4.1 vs §7.4

第 0 步让 `Main` 只依赖 `AgentSink`；第 4 步之后又有完整的事件流。两份输出描述的是同一件事（AI 开始输出、工具状态变了、出错了）。`AgentSink.notify` 与 8.17 的 `Notice` 事件更是同一个通知的两个来源——正好踩中 11.3 新加的"同一个状态存在两个来源"。

**建议**：在 4.1 明说 `AgentSink` 是**过渡件**：第 0-3 步用它把链摘出 UI，第 4 步起改由投影层发布事件、Swing 侧退化为一个普通订阅者，端口随之删除（或只剩窗口级回调）。不写这句，后续实现会同时维护两套出口。

#### N6 [P1] `submit` 默认"拒绝"与插件注入的"并入当轮"不一致

**位置**：8.14 vs `Main.apiInject` / `PENDING_BG_DELIVERY`

8.14 定"会话忙时默认拒绝，并保证 `UserMessageRejected` 一定发出"。但现有注入路径（`Main.apiInject`，`Main:168-182`）走的是**并入当轮**：先记 `PENDING_BG_DELIVERY` 再抢锁，由在跑的链在下一轮快照里消化（`Main:378-387`、`:516-527`）。插件 `AgentJavaSessions.inject` 就是这条路径。

同一份状态、两个入口、两种语义：前端 submit 被拒，插件 inject 却能塞进去。实现 8.14 时要么改掉插件行为（外部调用方会感知），要么承认两个入口语义不同并写进契约。

**建议**：在 8.14 补一句"`AgentJavaSessions.inject` 保持并入当轮，不参与 `submit` 的拒绝策略"，并说明理由（外部调用方拿不到前端那套 PENDING 回滚）。

#### N7 [P1] `RoundFinished` 表达不了"链还有续轮"，`SessionStatus` 推导未定义

**位置**：7.4 `RoundStarted/RoundFinished/RoundCancelled`、§6 `SessionStatus`

现有代码里"轮"和"链"是两个层级：`loop()` 每轮调一次 `doStream`（`Main:223-247`），工具结果驱动 `requestContinue` 续下一轮（`:507-510`）；生成态则是**链级**——每轮开头 `setConversationGenerating(true)`（`:226`），链收束时统一 `false`（`:250`）。

于是按现在的投影：

- 带 3 次工具调用的链会发 3 组 `RoundStarted/RoundFinished`，前端在第一次 `RoundFinished` 后就会认为"这轮结束了"，而后面还有续轮；
- `SessionStatus.RUNNING` 没有推导规则：按轮推导会在每轮之间闪 IDLE，按链推导又没有链级事件可用；
- 取消也有两个时刻：`cancel` 返回 ≠ 链收束——已派发的工具还要 `toolCalls.forEach(join)`（`:503`），最长等 60 秒超时（`:73`、`:644-647`）。`RoundCancelled` 到底发在哪个时刻，8.6 没说。

**建议**：`RoundFinished` 增加 `boolean chainEnded`，或补 `SessionStatusChanged(sessionId, SessionStatus, seq)`；并在 8.6 写明"`RoundCancelled` 在链收束时发出，`cancel()` 只置取消意图"。

### 7.3 遗留问题（上轮未覆盖或仍未定，6 条）

#### R1 [P2] 空仓库自动建会话 + `activeId` 的归属

7.3 删了 `selectSession`，§6 又把"当前会话"划为前端私有（8.11）。但 `ConversationStore` 仍持有 `activeId`，且 `getActive()`（`ConversationStore:64-79`）在仓库为空时会**自动建一个会话**——一个"查询"带写副作用。`snapshot()` 若走 `getActive()`，空仓库的第一次查询就会造出会话并触发 `SessionCreated`。

**建议**：明确 `activeId` 由谁维护（核心保留给 Swing 用？还是彻底删掉）；`snapshot()` / `session()` 必须是只读的，空仓库返回空列表而不是建会话。

#### R2 [P2] `defaultEffort` / `defaultMode` 让核心依赖前端展示态

4.1 的端口要前端提供"默认思考强度/权限模式"，来源是 `window.getSelectedEffort()`（`Main:353-356`）——即输入区当前选中值。这是**展示态**，8.11 刚把它划成前端私有。无头模式下没人可问，返回值未定义，而它直接参与请求构造。

**建议**：旧会话的回落值改由核心配置提供（`settings` 里的默认 effort/mode），或要求 `submit` 前必须先 `setReasoningEffort`/`setAgentMode`；端口里的这两个方法可以删。

#### R3 [P2] 会话级 setter 是否发 `ConfigChanged` 未定义

8.12 只说"`RuntimeConfig` 的 setter 必须产生 `ConfigChanged`"。但 `setModel` / `setWorkspace` / `setReasoningEffort` / `setAgentMode` 在 `AppCommands` 上（7.3），不在 `RuntimeConfig` 里。按字面理解它们不发事件——那么两个前端同看一个会话时，一侧改了模型另一侧不知道，正是 8.12 想避免的问题。

**建议**：把 8.12 的适用范围改成"所有 setter"，或明确会话级变更由哪条事件承载。

#### R4 [P3] 三处措辞与悬空引用

- 4.3 第 98 行："`Conversation` 内部的 5 个同名方法……需要同步改，其中后两个按 `callId`，保持不动"——"5 个需要改"与"后两个不改"自相矛盾，实际是改 3 个。
- 十三引用"决策 13（待增）"，但 §9 决策表只加到 12 条，13 悬空。
- 11.2 判据改成"同一个方法里并排多个 `String` 则没有"，而 `setModel(sessionId, profileName, modelName)` 是三个相邻 String、`MessageView` 的构造也是。判据要么再收窄（排除 id/文本这类天然字符串），要么承认它只管"可枚举的取值"。

#### R5 [P3] 会话列表的排序规则没写

`ConversationStore.appendMessage` 会把会话挪到列表首位（`:179-181`），`setPinned` 只改标记不动顺序（`:152-160`），侧栏渲染时置顶优先。这套规则是核心顺序还是前端派生？`Snapshot.sessions` 的顺序是不是契约一部分？`sessionsSince(seq)` 只回变更项，前端要维护顺序就必须知道规则。

**建议**：写一句"`Snapshot.sessions` 按 `pinned` 优先、其次 `updatedAt` 降序；前端可自行重排，核心不保证增量顺序"。

#### R6 [P3] 工具消息的 `MessageState` 未定义

`MessageState` 五态是给聊天消息设计的。工具消息同时有 `ToolState` 七值，两个状态维度叠在同一条 `MessageView` 上：工具消息的 `state` 恒为 `CONFIRMED`？取消时是 `CANCELLED`？`MessageState` 与 `ToolState` 冲突时以谁为准？

**建议**：加一句"工具消息的 `state` 恒为 `CONFIRMED`（或 `CANCELLED`），生命周期以 `ToolState` 为准"，避免前端写两套判断。

### 8.2 新发现（v0.3 引入 / 未闭合，10 条）

#### T1 [P0] 工具句柄仍然缺失，`appendToolCall` 返回 void

**文档位置**：4.1 的 `AgentSink` 及其下方"六个方法的形状"表。

**代码依据**：`Window.ToolCallHandle` 有四个方法（`Window.java:963-985`），`Main` 四个全用了：`appendArgs(delta)`（`:453`）、`markExecuting()`（`:467`）、`requestApproval(decision)`（`:571`）、`finish(result, success, arguments)`（`:652`）。

**影响**：端口只覆盖了第三个，而且只是 sink 级的阻塞审批，不是卡片句柄。第 2 步接上端口之后：参数增量不显示、执行阶段标记丢失、**终态结果无处回填**——`finish` 是唯一把结果落库并翻卡的入口。这与上轮 N1 的"`appendAi` 返回 void 导致断流"是同一个错误，只是从 AI 侧挪到了工具侧，所以补了 `AiWriter` 也没解决。

另一个旁证：`appendToolCall` 的 `argsSummary` 形参在主链上恒为 `""`（`Main:625`），参数其实来自 `FunctionToolCallDeltaEvent` 的增量。端口照抄了一个永远为空的入参。

**建议**：`appendToolCall` 改为返回 `ToolWriter`：

```java
interface ToolWriter {
    void args(String delta);                 // 对应 appendArgs：仅展示，内部节流
    void executing();                        // 对应 markExecuting
    void finish(String result, boolean success, String arguments);
}
```

`argsSummary` 从签名里删掉（终态参数随 `finish` 走），初态由 `MessageAppended` 带 `ToolState.RUNNING`。

顺带一条判据问题：现在的完成判据是"`Main` 中 `window.` 归零"，但 `Main` 里仍有 **16 行** `Window.AiStream` / `Window.ToolCallHandle` 出现在方法签名与局部变量上（`:229, 262, 264, 394, 405, 409, 444, 455, 552, 561, 599, 607, 615, 622, 625, 635`）。`window.` 归零而 `import frontend.gui.Window` 还在，端口就白抽了。判据应改成"`Main` 不再 import `frontend.gui`"。

#### T2 [P0] `activeId` 判给前端了，但两条 core 行为靠它

**文档位置**：8.15 末段 + 7.3"没有 `selectSession`" + 8.11。

**代码依据**：
- `newConversation` 复用"当前空会话"并改 workspace（`ConversationStore.java:83-101`），判断依据是 `findById(activeId)`（`:84`）
- `switchTo` 删除离开的空会话（`:127-136`）
- `fork` 把新会话设为当前（`:225`），`remove` 重挑当前（`:165-169`）

**影响**：8.15 一边保留"创建时复用空会话""离开空会话会删它"，一边宣布"核心不再把 `activeId` 当状态树的一部分"，而 7.3 又删掉了 `selectSession`。三条合起来，core 没有任何途径知道当前会话是哪个：

- `createSession(String workspace)` 没有当前会话入参，"当前是空会话就复用"无法实现，`reused` 只能恒为 false；
- "离开空会话删它"没有"离开"这个信号，永远不会触发；
- `forkSession` 之后谁是当前、`deleteSession` 删掉当前后落到哪个会话，全都没有定义。

**建议**：把两个副作用改成显式命令，不要依赖隐式的 current：

- `createSession(String workspace, String reuseIfEmptySessionId)`：前端传入"我正在看的会话"，null = 永不复用；
- `deleteSessionIfEmpty(String sessionId)`：前端切走时自己调，或直接删掉这条产品行为；
- `forkSession` / `deleteSession` 的返回值带上"建议切到哪个 id"，由前端决定跟不跟。

这样 `activeId` 才真的能从共享状态里消失，8.11 的论证也才成立。

#### T3 [P1] 解耦只做了出站方向

**文档位置**：4.1 的触点表与完成判据。

**代码依据**：表里 9 类都在出站链路上，而 `window.` 实际覆盖 16 个方法、23 处调用。出站漏了三个：`setUsageInfo`（`:540`，用量胶囊）、`onBackGroundTaskKilled`（`:119`，后台终止翻卡）、`injectUserMessage`（`:176` 的 `w.injectUserMessage`，`apiInject` 的落点）。入站一个都没提：`onInputSubmitted`（`:95`）、`onRegenerate`（`:98`）、`onStopRequested`（`:100`）、`setBackGroundTaskControl`（`:112`），最后这个还带一个 Window 内嵌类型 `Window.BackGroundTaskControl`。

**影响**：`AgentSink` 是纯出站端口。要让 `window.` 归零，`main()` 里那四段回调注册必须搬出去，`Main` 只留无头也成立的部分；`BackGroundTaskControl` 还要反向定义（core 出接口、Swing 实现），否则这个类型继续从 UI 指回 core。这不是"再加一个端口方法"能解决的，是一次文件级搬迁——落地顺序里没有这一步。

**建议**：4.1 补一句"入站方向由组合根承担：`main()` 拆成 `CoreMain` + `SwingApp`，后者负责 `new Window`、注册回调、实现 `AgentSink` 与 `BackGroundTaskControl`"；完成判据改成"`Main` 不 import `frontend.gui`"，并说明 `setVisible` 这类生命周期调用归组合根。

#### T4 [P1] 端口在第 4 步退役，替代品在第 5 步才到

**文档位置**：4.1"第 4 步起由投影层发布事件……端口随之删除" + §12 第 4、5 步。

**影响**：`AgentSink.notify` 承载三处错误提示（`Main:198/476/484`：启动失败、流式错误、流式异常）。第 4 步删端口时，`Notice` 还在待补清单里（8.17，第 5 步才补），中间这段错误提示没有出口——而第 4 步的验收标准恰恰是"能连续跑 3 轮"，出错时会静默。`setRealtimeInfo`（停止时的"正在等待工具收尾…"）连第 5 步都没有对应事件。

**建议**：把 `Notice` 提前到第 4 步（它就是一个 record 加一处分发），或把端口退役推到第 5 步末。`setRealtimeInfo` 要么并进 `Notice(INFO)` 并接受语义变化，要么明确它归前端本地（停止按钮的即时反馈，不必过核心）。

#### T5 [P2] 工具结果在投影里的载体没写

**文档位置**：7.4 的 `ToolStateChanged.resultText`、§6 的 `ToolView`、8.3、8.10。

**代码依据**：工具结果存在 `Message.text`（`Message.java:5` 类注释："工具调用消息（role=tool）的 text 存工具结果"）。

**影响**：三处对不上：

1. `ToolView(callId, name, argsSummary, state)` 没有结果字段，`MessageView.text` 对工具消息该放什么，8.3 只定义了 USER / ASSISTANT；
2. 一个只重连、不重放事件的前端，`session(id)` 里能否拿到工具全文，取决于投影有没有把 `text` 填上。不写就会有人按"text 只给聊天消息"实现，工具卡永远空着；
3. 8.10 要求"截断必须可见"，但 `ToolStateChanged` 和 `MessageView` 都没有这个字段，决策 13 又把截断本身挂起了。

**建议**：8.3 补一行 TOOL_RESULT——`MessageAppended` 时 `text` 为空，终态由 `ToolStateChanged.resultText` 推送，快照里 `MessageView.text` 是同一份数据（不截断时）。截断标志若要保留，`ToolStateChanged` 加 `boolean truncated`、`MessageView` 同步；若决定挂到决策 13，就从 8.10 挪进待补清单，别在正文留一条没有字段的硬要求。

#### T6 [P2] 审批的两条要求在类型上无处落地

**文档位置**：8.8 的三条契约 + 7.5 的 `Request` / `HostRequestClosed` + 4.1 的 `requestApproval`。

**影响**：

- "`Request.deadlineEpochMs` 必须填，超时后的动作由决策 5 定"——但 `ToolApprovalGate.allow` 是无超时阻塞（`Main:551-597` 的 `while (!cancelled.get())` 里 200ms 轮询），端口的 `requestApproval` 也没有 deadline 形参。核心没有能力在超时后收回等待，这个字段只能是装饰。
- "每次自动拒绝都要产生可审计的记录（日志或 `HostRequestClosed` 附带原因）"——`HostRequestClosed(requestId, sessionId, seq)` 没有 reason，括弧里的第二个选项实现不了。

**建议**：`requestApproval(..., long deadlineEpochMs)`，由端口实现在 deadline 到达时返回 null 或拒绝；`HostRequestClosed` 加 `CloseReason { ANSWERED, TIMEOUT, AUTO_REJECTED, CANCELLED }`。或者明确"超时由 gate 自己算、事件只记结果"，那 8.8 的措辞要跟着改。

#### T7 [P2] `defaultEffort` 换了来源，但没定前端显示什么

**文档位置**：7.6 新增的四个方法 + §6 的 `SessionView.effort`。

**代码依据**：`SessionView.effort` 是 `ReasoningEffort`（非空），投影必须把 null 解析成某个值；而 Swing 侧 `restoreConversationOptions` 对没盖过戳的会话是"保持当前选中不动"（`Window:1385-1402`）。

**影响**：如果投影解析成 `defaultEffort`，输入区却继续显示上一次的选择，就会出现"用户看到 HIGH、实际发出 MEDIUM"——正是 11.3 的"同一状态两个来源"。另外文档给的理由（"读的是展示态"）比实情轻：`stampConversationOptions` 只在发送/重新生成时盖戳（`Window:2110, 2654`），`apiInject` 与后台续轮起的链读的是**当前显示会话**的下拉，是跨会话串台，不只是"展示态"。

**建议**：写明 `SessionView.effort` / `mode` 是**生效值**（投影时解析 `null → default`），前端一律按它渲染输入区；`setReasoningEffort(sessionId, null)` 是否允许"恢复默认"一并定掉。

#### T8 [P3] `GapDetected` 的记录体编译不过

`record GapDetected(long sinceSeq, long earliestSeq, long seq) implements StateEvent {}`——`StateEvent` 声明了 `String sessionId()`，这个 record 没有该分量，空体不会生成实现。需要显式写 `public String sessionId() { return null; }`，或加一个 `String sessionId` 分量（但那与"恒为 null"矛盾）。上轮 `SessionCreated` 踩的是同一个坑，当时靠补分量解决。

#### T9 [P3] 两个 `callId` 方法保留，但事件要 `messageId`

4.3 决定 `completeBackGroundTask` / `terminateBackGroundTask` 继续按 `callId`（对，后台回调线程只有 `callId`），但 `ToolStateChanged` 的必填项是 `messageId`。core 必须自己维护 `callId → messageId` 的索引，或在两个方法里带回消息。契约应写一句："`callId` 是外部句柄，`messageId` 由 core 解析；事件里两个都给，前端以 `messageId` 为准，`callId` 只用来挂审批。"

#### T10 [P3] 小项

- 8.15 开头"现有两处刻意为之的产品行为"，下面列了三条（第三条是约束，不是行为）。
- `ConfigChanged(key, sessionId, seq)` 不带新值，前端收到后必须重拉 `session(id)` 或 `profiles()`；不写，JS 侧会等一个永远不来的值。
- `session(id)` 对不存在的 id 返回 null 还是抛异常，未定（外部调用方要处理）。
- 8.5"其所在链被取消时为 `CANCELLED`"：是链上所有工具消息，还是只在飞的那条？前者要给 core 加一次扫描改写。

### 8.3 第三轮结论

| 项 | 判断 |
|---|---|
| 修复质量 | 仍然高。N3 / N4 / N6 / N7 / R5 / R6 都是照着源码改的，`chainEnded` 与链级 `SessionStatus` 这一对尤其准 |
| 主要问题 | 两条 P0 都是"同类错误换位置"：N1 修了 AI 句柄、漏了工具句柄；R1 把 `activeId` 判给前端，却留着依赖它的行为 |
| 是否可进入实现 | **不**。T1 让第 2 步的工具卡失效，T2 让第 0 / 1 步的 `createSession` 无法实现 |
| v0.4 建议范围 | T1 + T2 + T4；T3 只需一段话和一句判据；T5 / T6 各补一个字段；其余挂账 |
| 顺序问题 | 第 0 步（消息 id）与第 1 步（状态树搬家）动的是同一批文件和同一段落盘兼容代码，先搬家再加 id 只改一遍。若不是刻意"先语义、后机械"以便二分定位，建议对调 |

顺带一个观察：三轮下来，问题集中在**"这份状态归谁"**——端口归 UI 还是 core、`activeId` 归前端还是 core、`defaultEffort` 从哪读、工具结果走事件还是快照。接口的形状本身已经稳定，剩下的是所有权。v0.4 若补一张"字段 → 所有者"的表，后面大概率不会再冒出新问题。
