# 踩坑记录

本项目前端（Swing）开发过程中真实踩过的坑，按"现象 → 原因 → 解法"整理。
相关代码位置都标了文件/方法名，改到对应模块前建议先扫一眼相关条目。

## 1. EDT 线程安全：后台线程碰 UI 会直接崩

**现象**：`ArrayIndexOutOfBoundsException: arraycopy: last source index 1 out of bounds`
抛在 `javax.swing.text.BoxView.replace`，且后续连锁 `NullPointerException`。

**原因**：Swing 的视图树（View/BoxView）不是线程安全的。调试工具曾从主线程调
`store.switchTo()` 触发 UI 重建，与 EDT 上的渲染并发操作同一个 JTextPane 的视图，
内部数组被写坏。之前几轮"侥幸没崩"只是时间差没撞上。

**解法**：所有 UI 操作必须进 EDT（`SwingUtilities.invokeLater / invokeAndWait`）。
`Main` 里的后端示例统一用了 `CompletableFuture.runAsync` + `SwingUtilities.invokeLater`
回 UI 线程的模板；Shot 工具所有窗口操作都包在 `edt(...)` 里。给 Window 写新接口时同样遵守。

## 2. 文本高度测量会污染正在显示的视图

**现象**：瀑布流卡片首选宽度变成 ~12.5 亿像素，用户卡片被排到视口外彻底消失。

**原因**：为了自适应高度，曾直接在**显示中的** JTextPane 上做
`view.setSize(width, Integer.MAX_VALUE)` 再读 `getPreferredSpan`。
这个调用会改写共享视图的内部状态，把首选宽度永久污染。

**解法**：`Window.measureTextHeight` 改为**一次性克隆一个 JTextPane**（同字体同文本）
在它身上测量，绝不碰显示中的组件。以后要做类似的"量文本"操作，一律走克隆。

## 3. 布局正反馈循环：面板越撑越大

**现象**：Debug 工具监听 resize 事件看到面板宽度 744 → 868 → 1012 → … 每轮 ×7/6，
一直涨到十几亿像素；把分隔条拖出来的用户卡片排到了 x≈7.8 亿的位置。

**原因**：连锁反应——
1. `fitCardHeight` 把"当前面板宽度"写成卡片的首选宽度；
2. 卡片首选宽变大 → 瀑布流面板首选宽变大；
3. `JViewport` 的规则是 **视图实际尺寸 = max(视口尺寸, 视图首选尺寸)**，于是面板被撑大；
4. 面板变大触发 `componentResized` → 回到第 1 步，滚雪球。

**解法**：卡片首选宽度恒为 0（高度写真实值），宽度完全交给布局器分配；
`fitCardHeight` 里留了注释说明这条红线。**任何子组件的首选宽都不要写回容器宽度。**

## 4. BoxLayout 的 alignmentX 是坑，换 GridBag 一了百了

**现象**：给用户气泡设 `alignmentX=1.0` 靠右后，配合 `Integer.MAX_VALUE` 的 max 宽，
面板首选宽度直接爆炸（BoxLayout 对非 0.5 对齐的子组件按 max 做对齐补偿）；
`Box.createVerticalGlue` 同样是无界 max 的来源。

**解法**：瀑布流从 BoxLayout 换成 GridBagLayout（`Window.rowConstraints`）：
AI 卡片 `fill=HORIZONTAL` 通栏，用户卡片 `fill=NONE + anchor=NORTHEAST` 定宽靠右，
行为完全确定。要再往瀑布流里加新元素（比如日期分隔行），继续用 GridBag 行，别回头用 Box。

## 5. Metal JButton：文字放不下会画成 "···"

**现象**：36px 宽的按钮上写"菜单"两个字，显示成三个点；`☰`/`⚙` 这类字符在宋体下
缺字形，同样糊成点。

**解法**：小按钮用单字符"≡"或短文字并 `setMargin(new Insets(0, 0, 0, 0))`；
图标类字符先用截图验证字形存在，不确定就用文字（现在 `Ui.button` 画的按钮都走这条路）。

**后续补坑（P1-4/P1-7 折叠三角，第二次踩）**：▸ ▸ ▶ ► 这类几何字符在
`new Font("微软雅黑", ...)` 里全部渲染成方框，截图回归一眼定位。这次把原因摸清了：
**物理字体没有回退链**——JDK 的逻辑字体（Dialog 等）缺字形会跨物理字体回退，
而直接指定"微软雅黑"拿到的是物理字体，缺字形就是 .notdef 方框，不回退。
别再猜字形了，用 `Font.canDisplay(codePoint)` 探针实测（踩坑 #11 的路数）：
实测微软雅黑只有 ▼ ▪ • 有，▸ ▸ ▶ ► ▷ 全缺。
**终极解是自绘**：折叠三角不依赖字体，`Ui.Chevron` 用 `fillPolygon` 画实心三角，
颜色走 `getForeground()` 跟随主题，两处折叠头部（工具卡/思考块）共用。

## 6. JSpinner 的灰底是 Metal 编辑区自带的

**现象**：给 spinner 设了白色背景，编辑区还是灰的；怎么调组件背景都没用。

**原因**：Metal 给 `JSpinner.DefaultEditor` 自带一层灰色边框/底色，盖在组件背景之上。

**解法**（`Ui.styleSpinner`）：`editor.setBorder(empty)` 清掉自带边框 +
文本域显式 `setOpaque(true) + setBackground(WHITE)`，组件背景再设白色兜底。

## 7. NumberFormat 改分组不刷新已渲染文本

**现象**：`format.setGroupingUsed(false)` 之后，spinner 里仍然显示 "4,096"。

**解法**：换一个带 pattern 的编辑器：`spinner.setEditor(new JSpinner.NumberEditor(spinner, "#"))`。
注意 `styleSpinner` 要在换完 editor 之后调用（它按 `getEditor()` 取文本域做样式）。

## 8. BasicSpinnerUI 的按钮要自己接线，且只接一次

自定义 `createNextButton/createPreviousButton` 返回的按钮不会自动带事件，
需要在里面手动 `installNextButtonListeners(button)`。曾担心和 UI 内部机制叠加导致
一次点击跳两格，用 `doClick` 测试验证：一次正好一个 step（0.5 → 0.6）。
以后改这段，重跑一遍这个测试。

## 9. 滚动到底部要等高度测量完

**现象**：切换到长会话后视口停在中部。

**原因**：卡片高度是布局后异步测量修正的；`scrollToBottom` 若在测量完成前执行，
`value/max` 都还不是最终值，滚不准。

**解法**：`showConversation` 只置 `pendingScrollToBottom = true`，
`fitAllCardHeights` 末尾才真正滚（`Window` 里搜这个标记）。窗口普通缩放不触发滚动，
不劫持阅读位置。

## 10. 零依赖 JSON（JsonKit）的边界

后端同学别拿它当通用库：只支持 null/布尔/数字/字符串/List/Map(String 键)，
不支持嵌套对象键、不支持注释。会话历史里全是字符串和长整型所以够用；
`ConversationStore.save/load` 有往返测试（Shot 里 PERSIST_OK 那段）兜底特殊字符。
以后要存复杂结构，优先考虑加 Gson 依赖而不是扩 JsonKit。

## 11. 调试方法沉淀

- **布局怪异先看组件树**：写个 DFS 打印每个组件的 `x/w/pref/alignX`（本轮的 Debug 工具思路），
  一眼就能看出"谁被排到了哪里、首选宽是多少"；
- **怀疑反馈循环就监听 resize**：对可疑面板 `addComponentListener` 打印每次宽度变化，
  如果在指数增长就是首选宽反馈；
- **截图回归发现渲染异常，别肉眼量坐标**：写个一次性 ImageIO 探针——按背景色扫描列找面板边界、
  或裁剪区域 3 倍放大看字形（Markdown 渲染这两招都用了），一分钟定位；
- **每次改 UI 跑一遍 Shot**（`foragent/tools/Shot.java`）：十五张截图 + 持久化/解析/流式落库/
  窗口化断言，比肉眼回归快得多，截图落在 target/ 下直接看；
- **测试工具断言失败要 `System.exit` 退干净**：AWT 线程不退会留下还能交互的"僵尸窗口"，
  中间状态没有脚本继续驱动，对着它滚动观察"复现"会被严重误导（P2-2 排查时亲眼踩过）。

## 12. StyledDocument 写入：字符属性要写全，分段靠 \n

**现象**：Markdown 渲染第一版截图里，标题、正文、列表项全部挤在一行；标题也没有放大。

**原因**：两个坑叠着——
1. 往 StyledDocument 连续 `insertString` 多个块，块之间没有插 `\n`：StyledDocument 用 `\n`
   分段，不插就全在同一个段落里；
2. 字符属性只设了 bold/前景色、没写字体族和字号时，回退的是 StyleContext 默认值
   （Dialog 12），**不是**组件字体——标题放大、行内代码切等宽全都静默失效。

**解法**（`MarkdownRenderer.fillFlow/fillQuote/insertSpans`）：块间显式补 `\n`；
每个 span 显式 `setFontFamily + setFontSize`，等宽块整包（family/size/fg/bg 全写）。

## 13. Markdown 强调的闭合边界检查只该约束下划线

**现象**：`**逐段**追加` 渲染成字面星号，完全不加粗；但 `**加粗**、`（后跟标点）正常。

**原因**：解析器给闭合标记加了"后面不能跟字母数字"的检查（本意是防 snake_case 里的
`_` 被拆成斜体），并把这条误套到了 `*` 上。CommonMark 里闭合 `**` 后跟汉字完全合法。

**解法**（`MarkdownRenderer.parseInline`）：边界检查只约束 `_`（前侧和后侧都是），
`*` 和 `~` 不做要求。这类 bug 光看解析断言发现不了（样例里强调后面都是标点），
是 Shot 截图放大后才现形的——**测试样例要覆盖"强调直连汉字"**。

## 14. 围栏代码末尾的换行会渲染成一个空行

**现象**：代码块底部多出约一行高的空白，测量值和显示却一致，排查半天。

**原因**：闭栏前的换行被当作代码内容保留，JTextArea 里它生成一整行空行框
（Monospaced 逻辑字体因中文回退行高约 1.9 倍，空行特别显眼）。

**解法**：`parseFence` 里剥掉末尾单个 `\n`（它只是语法分隔，不进展示、也不进剪贴板）。
另外量代码高度时记得 JTextArea 的 root view span **不含**组件 border，上下内边距要手工加回。

## 15. BorderLayout 容器塞"浮层"的两个坑（卡片右上角"…"按钮）

**现象**：给消息卡片加右上角悬停"…"按钮。第一版 `card.add(menuButton)` 不带约束——
所有卡片内容直接空白；第二版换自定义约束字符串 `add(menuButton, "overlay")`——
启动即抛 `IllegalArgumentException: cannot add to layout: unknown constraint`。

**原因**：
1. BorderLayout 对无约束的 add **当作 CENTER**，第二个 CENTER 子组件会**顶掉**第一个的布局
   登记：原内容组件从此没人布局，bounds 永远是 0，肉眼就是"内容消失"；
2. 未知约束名不是静默忽略，是直接抛异常（第一印象来自 GridBag/其他布局器，记串了）。

**解法**（`Window.OverlayCardLayout`）：别在 BorderLayout 上想办法，自己写 LayoutManager2，
三段（NORTH/CENTER/SOUTH）的排布规则照搬 BorderLayout（南段钉底、中段撑满余量），
浮层不进任何区域、坐标由 `layoutContainer` 末尾统一给。悬停显隐不占排版空间，
卡片高度全程不抖。**教训：往现有布局器塞"游离"组件没有捷径。**

## 16. 父容器悬停显隐：进出子组件会触发假 exited

**现象**：卡片 mouseEntered 显示"…"、mouseExited 隐藏，但鼠标从卡片滑进卡片内部的
文本区/按钮时，卡片先收到 exited，按钮闪烁或消失。

**原因**：Swing 的 entered/exited 按"最深组件"派发，跨进子组件边界就是父组件的 exited。

**解法**（`Window.attachHoverMenu/isPointerInside`）：exited 时不直接藏，取
`MouseInfo.getPointerInfo()` 的屏幕坐标判断是否还在组件 bounds 内，在就保持显示。
组件可能已被移除，`getLocationOnScreen` 要兜 `IllegalComponentStateException`。

## 17. Swing 的 HTML 不认 `<mark>`，行内背景要写 span 的 CSS

**现象**：侧栏搜索高亮按计划书里"现有 HTML 渲染器已支持 `<mark>`"的假设，用
`<mark>` 包命中词，截图里命中词完全没有底色——文字照常显示、不报错，纯静默失效。

**原因**：JLabel/DefaultListCellRenderer 的 HTML 支持是 HTML 3.2 方言，`<mark>` 是
HTML5 标签，解析时被直接丢弃；行内背景色得靠 `<span style='background-color:...'>`
的 CSS（InlineView 支持）。带不带 style 都一样，标签名不认识就整个没用。

**验证/解法**（`Sidebar.MARK_OPEN/highlightHtml`）：拿不准的标签先写一次性 ImageIO
探针按目标底色扫像素（踩坑 #11 的办法）——实测 `span+CSS` 底色正常渲染，
`<mark>` 两种写法都没有。和踩坑 #12 一路：**HTML 方言不认的写法不报错，标签和
CSS 属性必须截图验证过才能用。**

## 18. JComboBox 值区灰底：BasicComboBoxUI 直接读 UI 默认表，无视组件背景

**现象**：给下拉框 `setBackground(Color.WHITE)` 后，选中值区域仍是一条 #EEEEEE 灰底；
把背景改成红色做对照实验，灰底纹丝不动——它根本不跟随组件背景。
另一个表现：聚焦时值区还会整条变选中底色。

**原因**（读 JDK 17 源码实锤，`BasicComboBoxUI.paintCurrentValueBackground`）：
值区背景用 `DefaultLookup.getColor(comboBox, this, "ComboBox.background", null)`
直接取 UI 默认表（Metal 下 = 238,238,238），**完全不读组件的 getBackground()**。
顺带排除两个嫌疑人：`LookAndFeel.installColors` 只覆盖 UIResource/null 背景，
先 `setBackground` 再 `setUI` 也能存活；值标签的底色最后会被
`c.setBackground(comboBox.getBackground())` 覆盖成组件背景，也没问题。

**解法**（`Ui.styleComboBox`）：覆写 `paintCurrentValueBackground` 改填
`comboBox.getBackground()`；`paintCurrentValue` 强制按 hasFocus=false 画，去掉聚焦选中底。
排查路数照踩坑 #11：像素探针确认色值 → 红底对照实验证明"不跟随组件背景" →
翻 JDK 源码实锤 DefaultLookup 直查。**Swing 组件"设了背景没生效"时，先怀疑 UI
实现里有没有绕过组件属性直查 UI 默认表的地方。**

**后续补坑**：同一招的第二个现场——**禁用**下拉的值区走 `ComboBox.disabledBackground/
disabledForeground`（默认白底黑字），深色下生成中置灰时三个下拉齐发白。`paintCurrentValue`
覆写管不到它（disabled 分支在父类里另取 DefaultLookup），最省事的修法是在 `Ui.applyTheme`
里 `UIManager.put` 按主题给值（与 ToolTip 两行同套路），一次修掉所有下拉。
再补一刀：`disabledBackground` 必须给**和值区一致**的输入底色——渲染器 label 不透明、
按自身背景整块填，给别的色（比如胶囊色）就会在文字底下透出一块更深的"垫子"。

## 19. 深色主题：没显式设过颜色的地方全是"默认浅色"，浅色下看不出来

深色主题（P2-1）截图回归揪出来的两类，共性是浅色主题下完全无症状：

1. **文本组件默认黑字黑光标**。`JTextPane`/`JTextArea` 不 `setForeground` 就是黑色前景，
   `setCaretColor` 不设就是黑色光标——浅色卡片上正常，深色卡片上直接隐形（用户消息、
   输入框、系统提示词全中）。同类：`JTextField` 不设背景时默认白底。
   **解法**（`Window.initInputArea`/`insertMessageCard`、`Ui.styleInput`/`styleSpinner`、
   `SettingsDialog`）：凡是比较入的文本组件，前景/背景/光标三个都显式设，别依赖默认值。

2. **JScrollPane 自己的背景会从边框内衬里露出来**。圆角边框（RoundBorder 只画线不填充）
   + CompoundBorder 的空白内衬之间那圈区域，涂的是 JScrollPane 的 `getBackground()`
   （默认浅灰白）。浅色下白圈贴白卡看不出来，深色下一圈白边特别扎眼。
   **解法**（`SettingsDialog` 系统提示词滚动区）：`scrollPane.setBackground(...)` 和
   `viewport.setBackground(...)` 要一起设，只设 viewport 没用。

验证方式照踩坑 #11：截图 + 按背景色扫像素。**做主题类改动时，"默认值"本身就是一种
硬编码——每个组件的颜色三件套（前景/背景/光标）都问一遍"深色下它是多少"。**

## 20. 光标会"拽屏"：展示型 JTextComponent 把外层滚动容器滚到失控

**现象**：长会话窗口化（P2-2）后滚动消息区，滚几格就被失控地拽向新物化的卡片
（用户描述"滚个几格就不受控制直接跳"）；回归工具里 `setValue(0)` 滚到顶后，
位置又自己匀速爬升回中部，永远停不住。

**原因**：文本组件 `setText`/插入内容时，Swing 会安排 `DefaultCaret.repaintNewCaret →
adjustVisibility(caretRect)`——里面有早退守卫"caret rect 在组件 bounds 内就 return"。
但组件**刚 add、bounds 还没排好**时（(0,0,0,0)），守卫失效，接着调
`scrollRectToVisible`，沿父链找到第一个 JViewport 执行——把整个瀑布流拽到那张卡片处。
窗口化让"新建文本组件"变成滚动过程中的高频操作，每次填充/摘除卡片都会重新触发一批拽屏，
形成正反馈。之前从未暴露：组件只在切会话时批量创建一次，布局稳定时早退守卫全部命中。
真实滚动也在中招，不只是测试脚本。

**排查**：怀疑滚动被"看不见的手"挪动时，给视口 change 事件打调用栈
（`new Throwable().printStackTrace()`），一眼看到 `DefaultCaret.adjustVisibility`。

**解法**（`Ui.displayTextPane`/`displayTextArea`）：展示型文本组件直接覆写
`scrollRectToVisible` 为空——纯展示组件没有任何"需要滚到可见"的场景，代码块内部
滚动走的是自己的滚动条不受影响；输入框等可编辑组件保留原行为。
**凡是"嵌在滚动容器里的只读文本组件"，都该走这套工厂，别裸 new。**

**后续补坑**：抽这个工厂时把 `setEditable(false)/setOpaque(false)` 留在了原调用点没搬进去，
结果所有卡片文本组件变白底可编辑——浅色下白底和卡片色几乎无差但矩形边缘扎眼（"用户消息
多了个白块"），深色下 Markdown 整块发白。**工厂方法的配套状态要在工厂里一次设全，
靠调用方逐个补必然漏。**

## 21. 浮层"看得见点不到"：add 追加到末尾的组件其实在 z-order 最底层

**现象**：消息卡片右上角悬停"…"按钮，可见但有一小块区域点击无响应（用户气泡上约四成
面积失灵），AI 卡片上同样存在只是不容易撞上。按钮明明是 `fillCard` 里**最后** add 的。

**原因**：这套 z-order 里 **index 0 才是顶层**——`findComponentAt` 按下标从小到大找，
下标 0 最先命中；`add()` 追加到末尾反而是最底层。按钮能看见纯属侥幸：盖在它上面的
正文组件（`displayTextPane`/JLabel）都是 `setOpaque(false)` 的透明背景，按钮从透明
区域"透"了出来。凡是按钮与内容 bounds 重叠的区域，点击都被透明的内容组件截走，
`findComponentAt` 逐点采样实测命中率只有 58%（按钮 28x20，与 CENTER/NORTH 重叠的
左下区域全 miss）。

**排查**：对按钮 bounds 内逐点采样 `card.findComponentAt(point)`，看哪些点返回的不是
按钮本身；`getComponents()` 打印 z-order 对质。

**解法**（`Window.fillCard`）：`card.add(menuButton, "overlay")` 之后补一句
`card.setComponentZOrder(menuButton, 0)`，采样命中率 100%，绘制顺序不变（绘制与命中
是同一套 z-order，本来就是顶层）。**凡是"浮层"组件（不占布局、叠在内容上），加进容器
后必须显式提到 z-order 0，靠 add 顺序想当然就是埋雷。**

## 22. 改了源码没重编：跑回归跑的是旧字节码，假失败反把排查带沟里

## 23. FlowLayout 单行排不下不换行也不折行：行尾组件直接出界被裁

**现象**：用户实测发现工具卡头部（FlowLayout 从左往右排：箭头→角色标→工具名→参数摘要→
状态徽标→允许/拒绝按钮）在窗口较窄时审批按钮被推到卡片外裁掉，看不见也点不到，
只有把窗口拉宽才能踩到"允许"。

**原因**：`FlowLayout` 只有一行——首选宽放不下时**既不换行也不折行**，超出的组件坐标
直接排在容器边界之外，`clipBounds` 之外的部分不绘制、命中测试也落不进去。这也是
参数摘要被截到 80 字仍然不可靠的原因：摘要只是"通常够短"，不是布局上的保证；
"保证可见"永远轮到排在前面的组件，排在最后的按钮恰恰是"第一个被牺牲的"。

**解法**（`Window.buildToolContent`）：头部换 `BorderLayout` 三段式——WEST
（箭头+角色标+工具名）与 EAST（状态徽标+审批按钮）按各自首选宽定位、**永不裁剪**，
两端重叠时后 add 的 EAST 在上层（绘制与命中一致），按钮永远完整可见可点；
参数摘要塞 CENTER（区域宽=卡宽-两端首选宽），空间不足先被裁的是它，
不够看就点头头部展开看全文（展开态新增"参数"全文区，帽 160px 内部滚动）。
**凡是"少一个都不可见就出功能性问题"的关键控件（审批按钮、停止按钮），
不许交给"排在前面的组件通常不会太长"来兜底——用布局机制保可见，或者钉在不变裁的位置。**

**补注（模型目录"图片"勾选框踩到）**：`isShowing()` 对**画在父容器裁剪区外**的子组件
恒为 true——子组件自身 visible + 父可见就是"showing"，出不出界不管。连带两个坑：
`uiHasShowingText` 类断言对被裁组件照样通过；截图里它就是空白。**"断言绿/截图在"≠"看得见"**，
排不下的行只能改布局（分行/改两段式），再把断言升级成带边界检查的变体（bounds ∩ 可视区）。
## 24. 滚动容器视图宽于视口时不跟踪：右缘直接硬裁，GridBag 加权列白背锅

**现象**：设置面板"模型服务"页在 560 宽对话框里字段右端/"删除"按钮被切掉约 48px，右缘
连卡片描边都看不见。目检+探针（逐层 dump 首选/实际宽）定位：页面视图首选宽 532，视口
只有 484——`JViewport` 默认 SIMPLE 模式下**视图保持自己的首选宽**，比视口宽的部分直接
落在裁剪区外（不绘制也不可点），跟 GridBag 怎么排没关系。

**背景量级**：WSLg 的窗口装饰吞掉左右各 38px——`new JDialog().setSize(560, …)` 的内容
面板实际只有 484 宽（最小对话框对照实测，`getInsets()=(38,38,38,59)`）。真机 Windows
装饰薄，同样的布局可能勉强放得下；**回归截图全部来自 WSLg，目检要以 484 为可用宽**。
任何"首选宽凑合着放得下"的行，在这套环境里都是贴边裁切。

**解法**：需要"宽度跟随视口"的视图实现 `javax.swing.Scrollable`：
`getScrollableTracksViewportWidth()=true`（+ `TracksViewportHeight()=false` 保竖向滚动）。
视图被压到视口宽后，多余宽度交给内部 GridBag 压缩到加权列（weightx=1）上：加权列收窄、
非加权列保首选，自动换行的 JTextArea 按视口宽重排——不再是"整块右缘硬裁"。
配套注意：
- **FlowLayout 永不换行（踩坑 #23）在压缩下更凶**：行首选宽必须 ≤ 压缩后列宽，否
  则行尾组件照样出界。按钮组排不下的修法不是缩按钮（字体回退后宽窄不稳），是分行
  （下拉一行、按钮组一行），行首选宽取各行 max，窗口再窄也稳。
- **压缩把亏空全压到加权列上**：给"占满剩余空间"的列设 weightx=1 是它唯一收窄通道；
  没有加权列时 GridBag 宁可溢出也不压缩。多个加权列按比例分。
- 排版自查别只看行序：**多控件共 gridy 会直接重叠**（漏接 `addRow` 返回值就是这种），
  断言抓不到，靠逐张截图目检抓。

## 25. 组件状态被构建期硬编码覆盖：同一个状态只留一个写者

**现象**：用户报"打开设置面板，模型删除按钮总灰着，必须切一下方案才点亮；重开面板还得再切"。
按钮可用态的推导逻辑（`syncModelButtons`：列表多于一项才可删）一直都在，初始加载也正确执行了。

**原因**：构造顺序**先加载后建 UI**——`loadSelectedProfile()`（会算模型删除按钮的可用态）
在 `buildProfilePage()` 之前跑；而 `modelRow()` 这个 UI 构建方法里还留着一行历史遗物
`modelDeleteButton.setEnabled(false)`（初版先建 UI 后加载时的"防误删"初值），把加载算好的
状态按灭了。之后切换方案走 `loadSelectedProfile → syncModelButtons` 重新同步，于是出现
"切一下就亮、重开又灰"的时钟式恢复——表面症状与真实根因（构建期覆盖）隔了两层排查。

**解法**：**一个状态只留一个写者**——`syncModelButtons` 是模型删除按钮可用态的唯一写者，
`modelRow` 这种布局构建方法里不许残留会改状态的语句（初值也不行：先有状态加载后有 UI 构建
的顺序下，初值就是覆盖）。同类写法自查：凡是"字段 A 的某状态"既有初始化又有方法 X 维护的，
初始化要么删掉（维护方首跑即正确），要么初始化改成"调用维护方"，不要各写各的。
回归钉法：打开即断言（在构造回 EDT 检查 `isModelDeleteEnabled`），而不是"操作一轮再检查"
——后者验到的是切换路径，不是打开路径。

## 26. Shot 裸类路径被跨包常量类打破：前端 store 引 backend.constant 连带 Jackson
3d1d03d 把 `Constants`（内含 Jackson `ObjectMapper`）挪进 `backend.constant`，`AppSettings`
为取 `APP_USER_DIR` 引用它——前端 store 的类加载从此传递依赖 Jackson。Shot 一直裸
`java -cp target/classes` 跑，`AppSettings.<clinit>` 直接 ClassNotFoundException，
症状在 Shot 的 clinit 行号上（不在任何新改动的方法里），第一眼像回归断言炸了。
**解法**：运行命令换 `java -cp "target/classes:$(mvn -q dependency:build-classpath \
-Dmdep.outputFile=/dev/stdout)"...`（写进 Shot 头注释）。**教训**：常量类里塞运行期对象
（ObjectMapper）会把"只是引用一个编译期常量"变成真依赖；跨包取纯常量时留意引入方运行
环境里有没有货，或者把纯常量与可变工具对象分家。
**补注（ad68322）**：MAPPER 收进惰性 holder（`getObjectMapper()` 调用点才初始化 Jackson）后，
加载 Constants 不再触发依赖——前端 store 只引 `APP_USER_DIR`/`DEFAULT_WORKSPACE_DIR` 两个
Path 纯常量，链上还有 JsonKit（自写极简 JSON，不碰 Jackson），本就不该缺货。运行命令已复归
裸 `java -cp target/classes`，Shot 全套断言实测复跑 SHOT_OK。教训落地形态：分家分在**调用链**
上——运行期对象别躺在常量类的 `<clinit>` 路径里（链上任何人的纯常量引用都会引爆），惰性
持有才是唯一解。

## 27. 粘贴才出的 ClassNotFoundException：源头是 IDEA 写剪贴板，打印者是 JDK 的 SystemFlavorMap
现象：往输入框粘贴时控制台冒出 `Exception "java.lang.ClassNotFoundException: com/intellij/..."
while constructing DataFlavor for: application/x-java-...`，每个类两条（objectref + serialized
两种 flavor 各一条）；看着像随机复现——启动后第一次粘贴有、之后按同样方式试又没有。

**排查路径**：message 措辞怪（引号后没空格），先怀疑自己的代码/tinylog——都不是；对运行时
镜像 grep：`jimage extract --include "/java.datatransfer/**" --dir x $JAVA_HOME/lib/modules`
后拿 `strings | grep` 定位到 `java.awt.datatransfer.SystemFlavorMap` 常量池里的字面量
`"while constructing DataFlavor for: "`——JDK 内部打印。第一次 grep 没找到是因为翻错了
模块档（翻的是 java.desktop，数据传输机制在 java.datatransfer 模块）。

**机制**：IDEA 复制内容时（哪怕你眼里是"纯文本"，从 IDEA 控制台复制日志也算）会往系统剪贴板
额外塞它的专有 flavor——`x-java-jvm-local-objectref; class=com.intellij...FoldingData` 与
`x-java-serialized-object; class=...EditorCopyPasteHelperImpl$...`。我们的 Swing 第一时间去读
系统剪贴板时，SystemFlavorMap 解码每种 native 格式 → 要在**我们的类路径**里加载 `com.intellij.*`
类 → 必然 CNFE → JDK 打印这条 + **丢弃该 flavor，其余照常**，粘贴本身零影响（text/plain 照拿）。
"神秘时隐时现"是两件事叠加：①触发条件=剪贴板最后被 IDEA 写过，之后换别处复制就永远安静；
②SystemFlavorMap 的 native→flavor 映射有软引用缓存，同一 flavor 第一次解码失败后就记住了，
同内容再贴不复现，重启应用（清缓存）或 IDEA 换一个专有类才再炸一次。

**两个教训**：(1) `getLogLevel` 调不下来这种"日志"——它不走 tinylog，是 JDK 内部直接打
`System.err`；"控制台有输出"先分辨管道（tinylog / System.err / JVM 原生 stderr）再动手，等级
选择器只管自家管道。(2) 排查这类"天花板在类库/运行时里"的输出，拿 jimage 把 modules 镜像
按模块抠出来 grep 常量池，比搜索引擎快且准——字面量里的怪格式（`"...while` 缺空格）本身就是
一眼认出源头的指纹。**处置**：不修；真嫌吵只剩一条窄口子（Main 启动包一层 System.err
过滤掉匹配该字面量的行）——过滤 stderr 会教人瞒报，没有干净实证之前不动它。

## 28. JList 组头渲染器里的子组件：CellRendererPane 不校验布局，且组件 bounds ≠ 可见宽，摆位要信 clip
现象：侧栏按工作区分组，组头行做了个双 JLabel 面板（GridBag：名字 weighting 列 + "＋"贴右缘）。
浅色主题下加号画得好好的；**换主题重建后"＋"整块失踪**，名字却还在——截图+像素扫描实锤不是
颜色对比度问题（前景深色主题蓝 #4E8BFF 理论可见），是那半根本没画。

**排查路径与连环翻转**：先怀疑颜色捕获/复用渲染器串台——离屏 printAll 抓出来也没有（主窗
实例）→ 缩到"Swing 内部就没画+"；受控探针（同包真 Sidebar+深色主题）printAll 却**有** →
同码不同命，把打印塞进 paintComponent 对拍：paint 确实在跑、宽高/前景都正确——转两手再给
paintComponent 里手动 drawString 同位置画"＋"+红点做对照，才看到 `[HDR-PAINT] clip=223 w=244`：
**paint 时组件自身 bounds（244，=列表宽）与 clip（223，视口可见宽）不一致**，"＋"摆在
x=227..244，整块落在裁剪区外"白画"。再补 `[HDR-LIST] listW/vpW` 对拍坐实：**JList 会被
会话行的首选宽撑得比视口宽**（长标题溢出裁切的历史行为），列表宽随内容浮动、可见宽恒等于
视口宽——浅色/深色不是变量，"当时有没有长标题行"才是（深色段恰好塞了长行探针文本）。

validate——靠异步 revalidate 给子组件摆位等于赌时序（换重建就露馅）；子组件摆位必须放进
`paintComponent` 里**同步** setBounds（或干脆整行单 JLabel 异体）。(2) 渲染器里想"贴右缘/
到底缘"，**永远用 paint 时 `g.getClipBounds()` 的宽**（命中区用 `getVisibleRect()`），
不要信 `getWidth()`——后者可能是上一次更宽布局的陈值。顺手排除过的歧路：Swing 的 HTML
表格 `width=100%` 不铺开、`float:right`/`text-align:right` 均无效（离屏对照实测），别再走
HTML 对齐路线。
